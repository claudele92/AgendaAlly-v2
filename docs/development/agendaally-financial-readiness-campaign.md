## 24. Proposed Refund State Machine

**Common transition contract:** immutable workflow/operation IDs; original allocation/context/payment and collector; beneficiary; exact amount, currency and frozen scale; policy/destination snapshot digest; current actor/tenant grant; expected version and command idempotency key. Every committed transition records server UTC timestamp, previous/new state and one immutable audit event. No transition may alter the approved amount, currency, original source or payee.

| From → to | Actor / prerequisites / evidence | Accounting / external movement |
|---|---|---|
| None → REQUESTED | Customer for own eligible collected payment; authorized scoped staff on behalf with provenance; stable request key; current unreserved refundable authority and fixed eligible amount | Reserve authority atomically; no Wallet credit and no external money movement |
| REQUESTED → APPROVED | Finance approval grant in source scope; source, entitlement, amount, currency and beneficiary rechecked; approval reason/actor recorded | Hold reservation; no payment/refund execution |
| REQUESTED → REJECTED | Finance rejection grant; mandatory reason | Release unclaimed reservation; no money moved |
| REQUESTED → CANCELLED | Requester for own pending/unclaimed request, or authorized Finance with reason | Release reservation; no money moved |
| APPROVED → CANCELLED | Finance only, with affirmative proof no execution claim/movement | Release reservation; prohibited after external execution responsibility is claimed |
| APPROVED → REQUIRES_REVIEW | Authorized Finance after an execution claim when outcome, identity or evidence is uncertain | Keep reservation; no completion claim; external movement may have occurred |
| APPROVED → COMPLETED | Assigned authorized completing Finance actor; valid prior approval; matched structured terminal execution evidence and unique external reference | Atomically append approved refund/reversal effects, consume reservation, record completion/evidence/event; external refund proven by authorized retained evidence |
| REQUIRES_REVIEW → COMPLETED | Finance reconciliation grant; same original approval/source; definitive matched execution evidence | Same one-time completion effect group; no redispatch |
| REQUIRES_REVIEW → REJECTED | Finance reconciliation grant and affirmative proof no money moved | Release hold; retain failed/uncertain attempt history |
| REQUIRES_REVIEW → APPROVED | Explicit Finance reauthorization only after proof the old attempt moved no money; fresh execution-claim event | Hold remains; no automatic retry |

An execution responsibility claim is a durable command while APPROVED, not another user-facing state. It prevents two operators acting externally on the same request. It cannot expire into permission to pay again automatically.

CANCELLED is justified by pending-request withdrawal. REQUIRES_REVIEW is required because manual execution and database recording are not atomic. Separate FAILED and PARTIALLY_COMPLETED states are deferred. Initial manual scope uses one fixed eligible amount per request, not an open partial-payment editor.

Prohibited: request → completed; rejected/cancelled/completed → approved; completed → requested; arbitrary status toggles; completion from a missing/unverified source; amount/currency/payee changes. Corrections are linked new events/operations, not terminal-state reset.

## 25. Proposed Payout State Machine

Use the same common immutable transition envelope and REQUESTED/APPROVED/COMPLETED/REJECTED/CANCELLED/REQUIRES_REVIEW meanings, with **beneficiary-owned matured payable**, not Customer refundable principal.

| Transition | Actor / preconditions | Accounting / movement |
|---|---|---|
| None → REQUESTED | Vendor for own verified Shop/beneficiary payable; Specialist only after an approved explicit entitlement contract; fixed original-currency amount and masked method/destination snapshot | Reserve unencumbered matured payable, not arbitrary Wallet display; no external payment |
| REQUESTED → APPROVED | Scoped Finance; eligibility and frozen method/beneficiary rechecked; approval evidence/event | Reservation retained; beneficiary not yet paid |
| REQUESTED → REJECTED/CANCELLED | Finance rejects with reason; requester cancels only own unapproved/unclaimed request | Release hold; no payment |
| APPROVED → CANCELLED | Finance, only before execution claim with known no movement | Release hold |
| APPROVED → REQUIRES_REVIEW | Claimed execution outcome uncertain | Retain hold; never tell beneficiary “Paid” |
| APPROVED/REQUIRES_REVIEW → COMPLETED | Authorized completing/reconciling Finance actor, prior approval, definitive receipt matching exact amount/currency/beneficiary/method and unique external reference | Consume held payable through one append-only payout settlement group; record immutable completion; external payment evidenced |
| REQUIRES_REVIEW → REJECTED/APPROVED | Respectively proven no movement, or explicitly authorized new attempt after proven no movement | Release/retain as appropriate; never blind retry |

Every row retains requested/approved/executed/recorded timestamps, actor attribution, command identity and audit history. Completed requests cannot be reopened or edited.

Initial smallest scope: one original allocation, one Shop, one currency and one beneficiary per request. No batching, FX or inferred Specialist commission. Vendor-direct money already held by the Vendor is not automatically a platform-funded Vendor payable.

## 27. Manual External-Execution Evidence Model

Required before COMPLETED: operation/workflow identity; actual execution UTC timestamp; exact executed amount and currency; method classification; institution/provider and scoped external transaction reference; beneficiary identity and masked destination fingerprint; original payment/payable linkage; terminal-success classification; retained private receipt/reference and server-computed SHA-256; completing Finance actor; attestation that receipt identity/amount/payee were checked; completion note; immutable server recording timestamp.

Pending/queued/initiated receipts are not terminal execution evidence. A free-text “paid” note alone is insufficient. Manual evidence is honestly classified as **authorized retained manual execution evidence**, not a provider-verified API transaction.

Use a private document store with scoped, expiring reads, file-size/type/malware checks, redaction and retention policy. Match the digest to the retained file rather than trusting a client-supplied hash. Avoid full bank/card details where a reference and masked fingerprint suffice; prohibit CVV, card numbers, bank login credentials, provider secrets and passwords.

Reference uniqueness is scoped by institution/method and stable payer-account identity under an approved reference contract. Do not include amount in that uniqueness key or allow a changed amount to reuse a payment. Shared statements need an individual execution identity; batched payments are deferred.

## 28. Idempotency/Replay Design

- Preserve the existing allocation/kind/request-key uniqueness and strict same-request comparison. Add one workflow per canonical operation.
- Each request/approve/reject/cancel/claim/complete/reconcile command has a durable actor-scoped key and canonical payload digest. Same key/same intent returns its recorded result; changed payload is a conflict. Browser refresh must retain the original intent until the user explicitly starts another.
- One durable execution claim prevents concurrent operators externally paying the same approved request. Unknown outcome keeps that claim/hold; no automatic expiry permits another payment.
- One completion per workflow/operation; unique institution-scoped external execution identity; one canonical completion effect group and one transition audit event per command/version.
- Replayed completion returns the already-recorded safe result, not another effect or notification. A different receipt/amount/beneficiary is rejected.
- Existing Product fulfillment financial finality remains independent of lifecycle status. Frontend button disabling is only convenience.

The application cannot make arbitrary bank actions idempotent. Operators must use the stable operation reference externally, check the execution claim and reconcile uncertain attempts before any new external action.

## 29. Transaction/Concurrency Design

| Mutation | Required transaction / locks | Failure and response |
|---|---|---|
| Request + reserve | Fresh owned transaction; original allocation mutex first; current authority, operation/workflow and required Wallet rows in stable order; check exact available authority; unique request/operation/workflow | All reserve/workflow/event writes roll back; no success if any required write fails |
| Approve/reject/cancel | Same parent mutex and operation/workflow locks; current authorization; expected state/version; unclaimed cancellation condition | Atomic transition plus hold/event change; stale/foreign/claimed action rejected |
| Execution claim | Independent committed conditional claim under locks; one actor and claim identity | Losing claim cannot act externally; no provider/bank call inside SQL transaction |
| Complete/reconcile | Parent allocation first, operation/workflow, required sorted Wallet rows, evidence/reference and effect-group uniqueness; verify original approval/claim and exact evidence | Evidence, terminal state, effects and audit commit together; failure reports completion not recorded—do not pay again |
| Notification creation later | After authoritative commit, durable event/outbox uniqueness; delivery separate from finance | Mail failure never rolls back or duplicates money |

Maintain a fresh MySQL REPEATABLE READ authority view: no ordinary monetary snapshot before the allocation mutex. Preflight authorization is not enough; revalidate through current/locking reads in the owned boundary. SQLite FOR UPDATE alone is not a concurrency guarantee; preserve actual write/CAS serialization and native uniqueness.

The existing reserveOwned entrypoint forbids an ambient transaction. Future orchestration must own one fresh outer transaction and use the lower-level reservation unit correctly inside it so reservation, workflow and event are atomic; it must not nest reserveOwned or commit a reservation before its workflow.

Retry only transaction/deadlock conflicts with the same command identity and bounded attempts. Never retry an external execution automatically. No response may claim completion after rollback, a missing required row or failed accounting effect.

## 30. Wallet/Accounting Boundary Design

Keep original gross, collection, fee, Vendor payable, custody and currency/scale snapshots immutable. Reservation reduces available entitlement; approval does not credit/debit principal. Completion consumes the reservation and appends the accepted original-context refund or payout effects once.

External refund returns principal and applicable original commission/adjustment shares under the accepted exact equations. External payout settles the appropriate payable; it does not transfer money between an Admin’s and recipient’s virtual Wallets to fabricate bank custody.

Customer gross, platform fees, Vendor payable, Specialist earning, refund liability, payout holds, cashback and actual bank/provider/cash custody are separate concepts. A Specialist role or booking b_sum is not a source of matured payable.

Existing native Wallet refunds remain separately identified internal restitution. Do not both return spendable Wallet credit and pay the same principal externally. New manual external refunds of originally Wallet-funded principal stay gated until the owner approves a redemption/cash-funding policy. Do not silently change accepted legacy Wallet semantics or reinterpret its display balance as redeemable bank money.

No implicit FX or rounding migration: amounts use the source’s frozen native money_scale, not a newly inferred ISO scale. Any unsupported currency/precision/method fails closed.

## 31. Booking Cancellation/Refund Design

| Booking/payment condition | Proposed financial result |
|---|---|
| Unpaid/uncollected | Cancellation only; release genuinely unfunded allocation/holds safely; no refund request for nonexistent collection |
| Cash selected, not confirmed | Cancellation only; selection is not collection |
| Cash explicitly confirmed with legitimate collection authority | Determine fixed refundable liability under accepted policy; manual request may be eligible only against proven collector/cash custody; cancellation itself never says refunded |
| Platform provider-paid | Bind eligible request to original verified captured payment, collector, merchant revision, currency/scale and existing policy |
| Vendor-direct provider-paid | Original collector remains the Vendor; no invented platform custody/funding. Finance must have a mandate and evidence from the actual executor |
| Native Wallet-paid | Preserve once-only internal refund/cashback behavior as internal credit, not external refund completion; external redemption separately gated |
| Non-refundable / reduced eligible amount | Preserve accepted cancellation/digital/fee policy and disclose fixed eligibility; no ad hoc amount editing or unsupported partial-completion product |

Display “Cancelled” independently of “Refund requested/approved/completed.” Existing refund_time or a negative payable adjustment is not an external receipt. Link one eligible cancellation intent to the original financial source; terminal refund/cancellation markers cannot be reset to repeat principal.

## 32. Product Fulfillment Financial Boundary

Retain the already-contained Order financial marker and source authority. Future events identify the Order, original allocation/payment and fulfillment financial intent, with a unique one-time settlement/effect identity independent of repeated delivered status.

Customer payment is collected once; fulfillment recognizes only the original eligible economics. Vendor entitlement and platform fee are not new gross collections. Canonical linked accounting must not also invoke legacy Admin gross credit.

Reversal/correction is a separate authorized append-only event linked to the original settlement, constrained by original authority and prior reversals. Never reset settled → pending to reuse the original payment. Unverified legacy Orders remain review-only until provenance is established.

## 33. Provider/Future Automation Boundary

Manual MVP execution does not call refund/payout APIs, create provider transactions, enable providers or depend on a webhook.

Existing collection methods retain all environment/global/country/currency/merchant/runtime/checkout gates. Configured/setup-available means neither active nor collected.

Original provider/context/revision/capture identity remains immutable. A later execution adapter may supply matched terminal evidence through a verified API, webhook or reconciliation, using the same business approval/finality and evidence boundary. It must not reinterpret manual operator attestation as provider verification.

Current RefundTransport deliberately rejects normal non-testing activation. Do not relax that gate or impersonate testing to implement manual completion. Adapter development/activation and unsupported provider contracts require separate approval.

## 34. Reconciliation Design

Minimum queues: requested; approved outstanding; claimed but not completed; requires review/unknown; completed; rejected/cancelled; stale/aged; and unmapped legacy records.

Filters: type, state, age, original Shop/country, currency, beneficiary, amount, source Booking/Order/Transaction/allocation, approval actor, execution/completion actor, external reference and execution/recording dates.

An operation detail shows immutable source terms, holds/available authority, approval and claim timeline, masked destination, evidence provenance and discrepancies. Flag missing/duplicate references, wrong amount/currency/payee, uncertain bank outcome and external execution without committed completion.

Do not release an unknown hold automatically or redispatch an uncertain payment. A separate reconciliation grant can match definitive evidence, prove no movement, or propose a linked correction. This is not a full ERP.

## 35. Audit-Trail Design

Append immutable events with workflow/operation ID, event/command identity, previous/new state, version, actual actor and grant/source scope, server UTC time, exact amount/currency/scale, original payable/payment, reason, snapshot/evidence digest and external reference where applicable.

Record execution claims and unsuccessful/uncertain attempts without overwriting the successful financial fact. State changes, effects and their required audit event are atomic. Replay must not add another audit event for the same committed transition.

Corrections reference original events and require explicit authority. Evidence access is audited separately. Do not log credentials, raw private documents or financial SQL bindings; keep source-generated error responses safe.

## 36. Admin/Finance UX Proposal

One permission-scoped queue with type, request ID, requester/beneficiary, Shop/source, amount/currency, state, age, request/approval/completion timestamps, method snapshot, claim owner, masked evidence/reference and eligible actions.

Dedicated actions: approve, reject with reason, cancel before execution, claim external-execution responsibility, record completion evidence and reconcile. **No unrestricted status dropdown.**

Approval confirmation explicitly says no money has moved. Completion requires the structured evidence form and an existing claim/approval. Unknown outcome shows “Do not pay again—reconciliation required.” Another operator’s claim blocks external action.

Source and destination snapshots are read-only. Evidence files require their own permission. No design preview, UI component, mutation action or template was built.

## 37. Customer/Vendor/Specialist UX Proposal

Customers see cancellation separately from refund status: requested, approved—not refunded yet, completed with safe receipt summary, rejected/cancelled or under review. Internal Wallet return is labeled as Wallet credit, not bank refund.

Vendors see verified payable, reserved amount, available authority and own payout status; approved explicitly says not paid out. Completion shows a safe external reference/date without revealing Finance documents or payer credentials.

Specialists see only their own authorized state. Where no authoritative Specialist entitlement exists, request is disabled with a truthful eligibility explanation; an assignment/statistic does not create a payable.

Own pending cancellation and discrepancy reporting are state-aware. No ordinary user self-approves or self-completes. No interface aggregates mixed currencies or fabricates external balances.
