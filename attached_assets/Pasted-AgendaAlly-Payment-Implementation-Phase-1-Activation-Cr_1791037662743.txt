============================================================
3. P1-A — PAYOUT CONSERVATION / ATOMICITY
============================================================

The audit found that the current Wallet-method payout flow can:

- manipulate an approving Wallet;
- perform another withdrawal/debit;
- persist payout status separately from the financial legs;
- ignore unsuccessful native service results;
- lack one encompassing financial transaction.

This creates a source-confirmed risk of:

- double debit;
- partial settlement;
- payout marked successful while financial effects are incomplete;
- inconsistent balances after failure.

Trace the CURRENT native payout flow before editing.

At minimum inspect:

- PayoutService;
- Seller payout controller;
- Admin payout controller;
- payout Store/Update requests;
- Payout model;
- Wallet services;
- WalletHistory;
- Transaction;
- observers/listeners;
- Vendor balance/payable sources;
- payout status transitions.

Do not assume the audit's summary substitutes for tracing the current source.

============================================================
4. REQUIRED PAYOUT INVARIANT
============================================================

For any payout operation that changes internal financial state:

THE FINANCIAL OPERATION MUST BE ATOMIC.

A payout must never reach an approved/paid/completed state unless every
required financial effect succeeded.

A failed payout attempt must not leave:

- payout status advanced;
- Wallet debit committed;
- duplicate debit;
- partial recipient credit;
- Vendor balance incorrectly reduced;
- Transaction committed;
- WalletHistory committed;
- payable/ledger mutation committed

unless that state is explicitly part of an existing safe pending lifecycle.

Native false/unsuccessful service results must be treated as failures where the
operation requires success.

Do not treat only thrown exceptions as failures.

============================================================
6. PAYOUT IDEMPOTENCY / REPLAY
============================================================

Determine the native payout lifecycle and ensure an already-completed payout

Verify at minimum:

- repeated approval;

- retry after rolled-back failure;
- Admin replay;
- Vendor replay where reachable.

Exactly-once financial behavior is required for the current payout mutation.

Do not create a new generalized payment-idempotency framework unless the
existing implementation genuinely requires it for this bounded containment.

The current disabled electronic-payment environment contains this path today,

Trace the exact CURRENT path before editing.

- service;
- actors;
- Booking ownership;
- Shop ownership;
- payment method;
- collection mode;
- provider;
- Transaction creation;
- status transition;
- provider verification requirement;
- downstream Booking settlement/accounting effects.

============================================================
8. AUTHORITATIVE ELECTRONIC PAYMENT RULE
============================================================

For an electronic/provider payment:

ELIGIBILITY IS NOT PAYMENT PROOF.

CONFIGURATION IS NOT PAYMENT PROOF.

PROVIDER SELECTION IS NOT PAYMENT PROOF.

TRANSACTION CREATION IS NOT PAYMENT PROOF.

A provider-backed electronic Transaction must not become authoritative `paid`
merely because:

- the payment method is active;
- the provider is eligible;
- configuration exists;
- environment policy allows the provider;
- a Customer selected it;
- a Transaction record was created.

Electronic payment success must require the existing provider-specific trusted
verification/evidence path.

Do not fabricate verification for providers that do not currently have one.

If a provider lacks authoritative verification, fail closed.

Ensure the correction is placed at the authoritative payment boundary rather
than hiding the problem in frontend state.
