2. OWNER-APPROVED MVP PRODUCT DECISIONS
======================================================================

The following decisions are now approved for this implementation.

2.1 INITIAL FINANCIAL SCOPE

One manual financial request represents:

- one authoritative original financial source/allocation;
- one beneficiary;
- one Shop where applicable;
- one currency;
- one fixed eligible amount;
- one financial workflow.

Do NOT implement:

- batching;
- FX;
- arbitrary amount editing after request;
- arbitrary partial-completion workflows;
- split beneficiary payouts;
- multi-Shop financial requests.

If the existing authoritative refund policy computes an eligible amount lower
than gross, that fixed computed amount may be used.

This is not an open manual partial-refund editor.

2.2 REFUNDS

Implement the manual Refund workflow for eligible authoritative collected
principal.

Cancellation and Refund remain separate concepts.

BOOKING CANCELLED != REFUNDED.

Refund approval does not mean money moved.

Refund completion requires authoritative terminal external-execution evidence.

2.3 VENDOR PAYOUTS

Implement Vendor payout requests only against verified matured Vendor payable.

Do not derive payout authority from an arbitrary Wallet display balance.

Do not treat an Admin Wallet transfer as proof of external payout.

2.4 SPECIALIST PAYOUTS

Do NOT activate Specialist payout requests in this MVP implementation.

The architecture may remain extensible to a future Specialist beneficiary, but
an assignment, Specialist role, booking statistic or displayed Wallet balance
does not establish a matured Specialist payable.

Specialist payout requires a separately approved earning/commission/maturity
contract later.

Fail closed.

2.5 WALLET-FUNDED PRINCIPAL

Preserve existing accepted internal Wallet refund semantics.

Do NOT implement Wallet-to-cash redemption.

Do NOT both:

- return the same principal as spendable internal Wallet credit; and
- externally refund that same principal.

Any future Wallet redemption policy requires separate owner approval.

2.6 CASH

"CASH selected" is not proof of collection.

Manual external Cash refund eligibility requires authoritative retained proof
that the Customer principal was actually collected under an approved Cash
collection authority.

If that authority cannot be proven, fail closed.

Do not infer collection from booking status or payment-method selection.

2.7 VENDOR-DIRECT COLLECTION

Vendor-direct collection remains custody of the original Vendor/merchant.

Do not fabricate platform custody.

A Vendor-direct refund may only proceed where the execution mandate and
evidence truthfully correspond to the actual collector/executor.

Do not fund a Vendor-direct refund from an invented platform liability.

2.8 LEGACY FINANCIAL STATES

Legacy:

- pending
- accepted
- canceled

must NOT automatically map to the new manual workflow's:

- REQUESTED
- APPROVED
- COMPLETED
- REJECTED
- CANCELLED
- REQUIRES_REVIEW

In particular:

LEGACY ACCEPTED != MANUAL COMPLETED.

Ambiguous historical records require reconciliation/manual review.

Do not fabricate completion during migration.

4. REFUND TRANSITIONS
======================================================================

Implement these bounded transitions.

NONE -> REQUESTED

Allowed only when:

- actor is authorized;
- original financial source is authoritative;
- collection is proven;
- beneficiary is correct;
- currency/scale are authoritative;
- eligible refundable amount is fixed;
- sufficient unreserved refund authority exists;
- request identity/idempotency is valid.

Atomically reserve the financial authority.

No external money movement.

No completion claim.

REQUESTED -> APPROVED

Finance approval permission required.

Revalidate:

- original source;
- beneficiary;
- amount;
- currency;
- eligibility;
- reservation;
- tenant/source authority.

Record approval actor/time/reason/audit event.

No money movement.

REQUESTED -> REJECTED

Authorized Finance only.

Reason required.

Release eligible reservation atomically.

No money movement.

REQUESTED -> CANCELLED

Requester may cancel own still-pending/unclaimed request where permitted.

Authorized Finance may cancel with reason.

Release reservation.

No money movement.

APPROVED -> CANCELLED

Finance only.

Allowed only when there is affirmative evidence that external execution has NOT
started and no execution responsibility claim prevents cancellation.

APPROVED -> REQUIRES_REVIEW

Use when an external execution was claimed/attempted but outcome or evidence is
uncertain.

Keep the reservation.

Do not claim refund completion.

Do not authorize blind retry.

APPROVED -> COMPLETED

Only an authorized Finance completion actor.

Requires:

- valid prior approval;
- valid execution responsibility claim;
- authoritative terminal execution evidence;
- exact amount match;
- exact currency match;
- beneficiary/destination match;
- original source match;
- acceptable method/institution;
- unique external execution identity/reference;
- immutable evidence/audit record.

Completion must atomically:

- record evidence;
- consume the held refund authority;
- append the correct existing canonical refund/reversal accounting effects once;
- transition workflow to COMPLETED;
- append immutable completion audit event.

No duplicate principal return.

REQUIRES_REVIEW -> COMPLETED

Only after definitive reconciliation evidence proves the original external
execution succeeded.

Do not redispatch money.

REQUIRES_REVIEW -> REJECTED

Only where authoritative reconciliation establishes that money did NOT move.

Release authority safely.

REQUIRES_REVIEW -> APPROVED

Only after authoritative proof that the previous attempt moved no money and
Finance explicitly authorizes a new execution attempt.

Never perform this automatically.

PROHIBIT:

- REQUESTED -> COMPLETED
- REJECTED -> APPROVED
- CANCELLED -> APPROVED
- COMPLETED -> APPROVED
- COMPLETED -> REQUESTED
- arbitrary status toggles
- completion without evidence
- amount/currency/beneficiary mutation after request

Corrections must be append-only linked events/new authorized operations.

5. VENDOR PAYOUT TRANSITIONS
======================================================================

Use the same business-state meanings for Vendor payouts.

NONE -> REQUESTED

Vendor may request only against:

- own verified Shop;
- own authoritative beneficiary identity;
- verified matured payable;
- sufficient unencumbered payable;
- fixed original-currency amount;
- approved payout method/destination snapshot.

Atomically reserve payable authority.

Do not use arbitrary Wallet display balance as the source.

REQUESTED -> APPROVED

Scoped Finance only.

Revalidate:

- Shop;
- beneficiary;
- matured payable;
- reservation;
- amount;
- currency;
- method/destination snapshot.

Approval is NOT payment.

REQUESTED -> REJECTED/CANCELLED

Release reservation safely.

No money moved.

APPROVED -> CANCELLED

Only before external execution claim and only with known no-movement evidence.

APPROVED -> REQUIRES_REVIEW

Use after claimed external execution where result/evidence is uncertain.

Keep payable reserved.

Do not tell Vendor "Paid."

APPROVED -> COMPLETED

Requires:

- prior approval;
- execution claim;
- authorized completing Finance actor;
- authoritative terminal external evidence;
- exact beneficiary;
- exact amount;
- exact currency;
- exact method/destination identity;
- unique external execution reference.

Atomically consume the held payable through the accepted canonical accounting
boundary and record completion/evidence/event once.

REQUIRES_REVIEW transitions follow the same no-blind-retry rules as Refund.

COMPLETED is terminal.

6. EXECUTION RESPONSIBILITY CLAIM
======================================================================

Implement a durable execution-responsibility claim.

This is critical.

Before an authorized Finance operator performs the external manual action, that
operator must claim execution responsibility for the APPROVED workflow.

Only one active execution responsibility may exist for the workflow/approved
execution attempt.

The claim must be committed independently before the operator is instructed to
move money externally.

A second operator must be prevented from independently executing the same
approved request.

The claim must record at minimum:

- workflow/operation identity;
- claiming Finance actor;
- claim identity;
- server timestamp;
- workflow version;
- command identity.

Do not make the claim automatically expire into permission for another payment.

If outcome becomes uncertain:

REQUIRES_REVIEW

not "available to pay again."

10. TRANSACTION AND LOCKING BOUNDARY
======================================================================

Preserve the accepted canonical financial locking hierarchy.

For request/reservation:

- own a fresh transaction;
- acquire original allocation/financial authority mutex first;
- lock operation/workflow;
- lock required Wallet/accounting rows in stable order where relevant;
- revalidate current authority under lock;
- reserve and create workflow/event atomically.

Do not call an entrypoint that independently commits a reservation before its
workflow exists.

Do not nest an incompatible reserveOwned transaction.

For approve/reject/cancel:

- lock authoritative parent;
- workflow;
- reservation;
- expected version/state;
- relevant source authority.

For completion:

- parent allocation/source first;
- financial operation/workflow;
- required Wallet/accounting rows in stable order;
- evidence/reference uniqueness;
- effect-group uniqueness;
- original approval/claim;
- current Finance authority.

Evidence + financial effects + reservation consumption + workflow finality +
audit event must commit atomically.

If a required database write fails:

ROLL BACK.

Never return success.

Never claim completion.

Do not automatically retry an external execution.

Database deadlock/serialization retry may retry the SAME DATABASE COMMAND with
the same command identity where safe.
