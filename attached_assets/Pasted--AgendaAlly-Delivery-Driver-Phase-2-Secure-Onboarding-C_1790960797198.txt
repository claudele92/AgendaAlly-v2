- impersonate the Driver.

The invitation must be associated server-side with the authenticated Vendor's authorized shop.

Never trust a submitted `shop_id` as authorization.

5. NEW DRIVER REGISTRATION
============================================================

============================================================
6. INVITATION SECURITY
============================================================

Reuse the existing secure invitation/token architecture where possible.

Otherwise implement only the smallest necessary secure mechanism.

Requirements:

- token must be unguessable;
- token maps to a specific invitation;
- invitation maps to the correct shop;
- acceptance maps to the intended authenticated person;
- expired invitations cannot activate membership;
- revoked invitations cannot activate membership;
- declined invitations do not activate membership;
- accepted invitations cannot be replayed into duplicate memberships;
- forged user/shop/invitation IDs cannot bypass authorization;
- cross-shop invitation access must fail.

Do not expose secrets or unnecessary account information.

============================================================
7. INVITATION / MEMBERSHIP STATES
============================================================

Reuse existing states where possible.

PENDING
Invitation exists but is not accepted.

ACTIVE
Invitation accepted and `driver_active = true`.

SUSPENDED
Invitation accepted but `driver_active = false`.

DECLINED / REVOKED / EXPIRED
Use where supported by the existing architecture.

Pending Drivers must NOT be assignable.

============================================================
10. OFFBOARDING / ACTIVE DELIVERY
============================================================

The previous audit identified active-delivery offboarding as unresolved.

Resolve only the minimum safe policy needed for Driver membership management.

A Vendor may deactivate a Driver from that Vendor/shop.

However, do NOT silently orphan an active delivery.

If the Driver currently has an active/in-progress delivery:

preferred behavior is to block final deactivation and explain that the active delivery must first be completed or explicitly reassigned using an existing safe mechanism.

Do NOT automatically select another Driver.

Do NOT silently cancel the order.

Do NOT alter financial records.

Historical completed orders must preserve their Driver attribution.

After successful deactivation:

- Driver receives no new assignments for that shop;
- shop-dependent operational access is removed;
- global account remains;
- relationships with other shops remain.

If existing order statuses make the correct active-delivery boundary ambiguous, fail closed and report it.
