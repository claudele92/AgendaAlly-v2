AgendaAlly — Implement Vendor-Owned Product Pickup Scheduling

Implement the next bounded fulfillment phase:

VENDOR-OWNED PRODUCT PICKUP SCHEDULING

This work builds on the Product fulfillment model already implemented:

1. Delivery
   → Customer delivery location/address.

2. Shop Pickup
   → Customer collects the Product order directly from the Vendor’s Shop/branch.

3. Collection Point
   → Customer collects from a separate supported collection location.

IMPORTANT:

Pickup scheduling in this task applies ONLY to:

SHOP PICKUP

Do NOT merge Shop Pickup with Collection Point.

Do NOT turn Collection Points into Vendor branches.

Do NOT apply Vendor Shop Pickup schedules to Collection Points.

Do NOT change Delivery scheduling/dispatch as part of this task.

Credit use is important.

Audit the existing implementation first, but do not repeat the broad Delivery/Pickup audit that was already completed.

Reuse the native fulfillment architecture implemented in the previous phase.

==================================================
1. GOAL
==================================================

When a Vendor enables Shop Pickup for Product orders, the Vendor should be able to decide HOW customers may pick up those orders.

Support two primary modes:

A. AS SOON AS READY

The customer does not reserve a specific pickup slot.

Conceptually:

Pickup timing

● As soon as the order is ready
○ Let customers choose a pickup window

The Vendor prepares the order and later marks it ready through the existing appropriate order workflow.

Customer sees something such as:

Pickup at shop

Wouri Beauty Bar
Rue Joss, Akwa, Douala

Pickup timing:
As soon as your order is ready

The customer should NOT have to choose a fake appointment time.

B. SCHEDULED PICKUP

The Vendor allows the customer to choose an available pickup date/time window.

Example:

Pickup at shop

Wouri Beauty Bar
Rue Joss, Akwa, Douala

Select pickup date

Mon  Oct 5
Tue  Oct 6
Wed  Oct 7
Thu  Oct 8

Available pickup windows

09:00 – 11:00
11:00 – 13:00
14:00 – 16:00
16:00 – 18:00

Customer chooses one valid window before placing the order.

==================================================
2. DO NOT MODEL PRODUCT PICKUP AS A SERVICE APPOINTMENT
==================================================

This is critical.

AgendaAlly already has Service booking/calendar functionality.

Do NOT create Product pickup by pretending that:

- an order is a Service;
- a Driver is a Specialist;
- a Vendor is a Specialist;
- a pickup is a booking;
- Product pickup consumes Specialist availability.

The domains are different.

Conceptually:

SERVICE BOOKING

Service
→ Specialist
→ Specialist availability
→ Date/time
→ Booking


PRODUCT SHOP PICKUP

Product cart/order
→ Shop/branch
→ Pickup policy
→ Preparation constraints
→ Pickup availability
→ Optional date/window
→ Product order

Shared calendar/date/time UI primitives MAY be reused where technically appropriate.

Shared generic scheduling utilities MAY be reused.

But Product Pickup must have its own authoritative availability/persistence semantics.

==================================================
3. AUDIT EXISTING SHOP / BRANCH MODEL
==================================================

Before implementing pickup schedules, determine what entity actually represents the physical pickup location.

Audit the existing:

- Shop;
- branch/location;
- Shop address;
- shop opening/business hours;
- fulfillment settings;
- Product order;
- order details;
- Delivery/Pickup selection;
- Collection Point model.

Do NOT create another branch/location model if AgendaAlly already has one.

If the current architecture supports only one authoritative Shop pickup location, implement against that safely and report the limitation.

If branches are already authoritative and suitable for fulfillment, pickup availability should be branch/location scoped rather than pretending all branches have identical schedules.

==================================================
5. DEFAULTS AND BACKWARD COMPATIBILITY
==================================================

Do NOT suddenly require existing Vendors with Shop Pickup enabled to configure a calendar.

Existing Shop Pickup behavior must remain valid.

Use a safe migration/default such as:

pickup_timing_mode = AS_SOON_AS_READY

for existing Shop Pickup configurations unless the existing data indicates another authoritative behavior.

That means existing Vendors continue accepting Shop Pickup without being unexpectedly blocked.

A Vendor explicitly opting into scheduled pickup can then configure scheduling rules.

Do NOT automatically enable Shop Pickup for Vendors that have not enabled it.

==================================================
6. PICKUP HOURS
==================================================

Audit existing Shop/business hours.

Where appropriate, allow pickup availability to start from or reference Shop hours.

However:

Shop business hours and Product pickup hours are NOT necessarily identical.

Example:

Shop open:
09:00 – 18:00

Pickup:
11:00 – 17:00

The Vendor may need preparation time before collections begin.

Therefore, preserve separate pickup availability where needed.

If providing a convenience action such as:

“Use business hours”

it should COPY/initialize the pickup schedule.

Do not permanently couple the records unless the existing architecture deliberately supports inheritance.

==================================================
7. PREPARATION / LEAD TIME
==================================================

Scheduled pickup must respect preparation time.

Example:

Current time:
10:20

Preparation time:
60 minutes

11:00–12:00 cannot be offered if the order cannot realistically be ready.

The earliest offered window must satisfy the configured lead-time rule.

For AS_SOON_AS_READY mode, preparation time may still be useful for customer expectations if the existing order model can support it safely.

Do not promise an exact ready time unless AgendaAlly can actually guarantee it.

==================================================
8. PICKUP WINDOWS
==================================================

Use pickup WINDOWS rather than appointment-style point times.

Examples:

09:00–11:00
11:00–13:00
14:00–16:00
16:00–18:00

Vendor configuration may define an appropriate window duration, for example:

30 minutes
1 hour
2 hours

Choose reasonable allowed values based on the existing time utilities.

Do not generate a huge unrestricted list of arbitrary minute intervals.

==================================================
9. SAME-DAY CUTOFF
==================================================

Support a Vendor rule for same-day pickup where practical.

Example:

Same-day pickup = enabled

Cutoff = 15:00

At 14:00:
eligible later windows may still be offered.

At 16:00:
today is no longer available.

The server—not only the frontend—must enforce this.

Do not trust a Customer-supplied pickup timestamp.

==================================================
10. BLACKOUT DATES
==================================================

Support Vendor-owned blackout dates for Shop Pickup.

Examples:

- holiday;
- inventory day;
- Shop closure;
- special event;
- temporary closure.

A blackout date should make scheduled Product Pickup unavailable for that applicable Shop/branch/date.

Do not alter Service Specialist availability.

Do not make the blackout automatically affect Delivery unless there is an existing explicit shared Shop closure mechanism that is authoritative for both.

==================================================
11. OPTIONAL CAPACITY
==================================================

Audit whether AgendaAlly already has an appropriate generic capacity mechanism.

If it can be implemented safely within this bounded phase, allow an OPTIONAL maximum number of Product orders per pickup window.

Example:

14:00–16:00
Maximum pickup orders: 5

Once five non-cancelled/non-terminal applicable orders occupy that window, it should no longer be offered.

However:

Do NOT invent a complex inventory/reservation engine merely for this.

If safe concurrency/capacity cannot be implemented with the current order architecture, leave capacity unlimited and document a concrete follow-up proposal.

Correct scheduling without capacity is preferable to unsafe pseudo-capacity.

==================================================
15. SERVER-SIDE AVAILABILITY
==================================================

The backend must be authoritative.

Create/reuse an appropriate availability endpoint/service.

Conceptually:

GET available Product pickup windows

Inputs may include:

shop/branch
date
cart/order context where necessary

Server evaluates:

- Shop Pickup enabled;
- pickup timing mode;
- Vendor ownership/configuration;
- pickup schedule;
- timezone;
- preparation time;
- same-day rule;
- cutoff;
- blackout date;
- optional capacity;
- applicable Shop/branch.

Return only valid windows.

Do not put the scheduling rules exclusively in React/Next.js.

==================================================
16. VALIDATE AGAIN WHEN ORDER IS CREATED
==================================================

This is critical.

Availability can change between:

Customer loading checkout

and

Customer submitting the order.

Therefore, when creating the Product order:

REVALIDATE the selected pickup window server-side.

Reject a stale/invalid selection safely.

Do not accept it merely because it was previously displayed by the frontend.

==================================================
17. STORE PICKUP INFORMATION AUTHORITATIVELY
==================================================

Audit the existing order/fulfillment schema.

Persist the necessary Shop Pickup information using the smallest clean extension.

Likely concepts include:

fulfillment type = SHOP_PICKUP

pickup location/shop/branch

pickup timing mode

pickup window start

pickup window end

timezone

Do NOT store formatted strings such as:

"Monday 2pm to 4pm"

as the authoritative scheduling value.

Store structured timestamps/values and format them for display.

For AS_SOON_AS_READY, do not fabricate window timestamps.

18. TIMEZONE

Do not silently use:

- browser timezone;

- server timezone;
- UTC as display time.

Store timestamps consistently according to the application's existing convention, while displaying them in the Shop pickup location's timezone.

Audit existing AgendaAlly timezone handling and reuse it.

23. MULTI-VENDOR CARTS

==================================================
24. SECURITY / TENANT ISOLATION
==================================================

Vendor A must never be able to:

- read Vendor B's private pickup settings;
- edit Vendor B's pickup schedule;
- create Vendor B's blackout dates;
- change Vendor B's preparation time;
- change Vendor B's capacity;
- manage Vendor B's Shop/branch pickup configuration.

Enforce ownership server-side.

Do not rely on Vendor UI filtering.

Forged:

shop_id
branch_id
schedule_id
blackout_id

must not bypass authorization.

Preserve authorized Admin/Superadmin behavior where intentionally supported.
