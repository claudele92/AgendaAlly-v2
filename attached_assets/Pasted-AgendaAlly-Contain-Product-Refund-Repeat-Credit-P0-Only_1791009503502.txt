============================================================
1. DEFECT TO CONTAIN
============================================================

The current Product refund lifecycle permits an authorized Vendor to:

accepted
→ pending
→ accepted

and each acceptance can create another positive Customer Wallet credit.

The original Order Transaction remains paid and there is no authoritative
once-only refund-settlement marker preventing repeated financial settlement.

This means refund STATUS and refund FINANCIAL SETTLEMENT are not currently
bound strongly enough.

The required invariant is:

ONE REFUND ENTITLEMENT MUST NOT CREATE MORE THAN ONE FINANCIAL REFUND CREDIT.

Changing lifecycle/status state must never make an already financially settled
refund payable again.

============================================================
2. TRACE THE NATIVE REFUND MODEL FIRST
============================================================

Before changing code, trace the complete current Product refund lifecycle.

Inspect at minimum:

- Product Order refund creation/request;
- Vendor refund status update;
- pending;
- accepted;
- rejected/canceled states if present;
- Customer Wallet credit;
- WalletHistory creation;
- Transaction creation/update;
- original Order Transaction;
- Order status;
- refund amount;
- commission/service-fee effects;
- payable/ledger effects;
- observers/listeners;
- Admin refund actions if they share the same settlement service.

Identify exactly which operation causes the Customer credit.

Identify whether any existing native field/state already represents:

REFUND FINANCIALLY SETTLED

or equivalent.

Prefer using an existing authoritative terminal state/invariant if one exists.

Do not add schema merely for architectural elegance.

============================================================
3. MINIMUM CORRECT CONTAINMENT
============================================================

Implement the smallest correct containment that guarantees:

A refund that has already financially settled cannot financially settle again.

Do NOT solve this merely by hiding a UI action.

The invariant must be server-authoritative.

Prefer preventing an accepted/financially-settled refund from transitioning
back into a state from which acceptance can create another credit, IF that is
consistent with the native lifecycle.

If the native architecture legitimately requires status movement after
financial settlement, then financial settlement itself must have an
independent once-only authoritative guard.

Determine which model is correct from the existing application before changing
it.

============================================================
4. STATUS MACHINE

- Can pending become rejected?
- Can accepted become pending?
- Can accepted become rejected/canceled?
- Can rejected/canceled become pending?
- Can any state re-enter accepted?

Financially dangerous backward transitions must fail closed unless the
application has a separate safe reversal model.

Do not invent refund reopening functionality.

============================================================

- platform payable/ledger adjustment.

The containment must ensure repeated acceptance, replay or status cycling cannot
