============================================================
2. TARGET CONFIGURATION MODEL
============================================================

ALL payment-provider credentials/settings must be manageable through the
application.

There are two credential ownership models.

A. PLATFORM-MANAGED

Admin configures AgendaAlly/platform provider credentials through the Admin
Panel.

These credentials may be used only for platform-managed collection.

B. VENDOR-DIRECT

Vendor configures that Shop's own provider credentials through the Vendor
Panel.

These credentials may be used only for that Shop's Vendor-direct collection.

There must be NO credential-owner fallback.

Platform credentials must never silently satisfy Vendor-direct configuration.

Vendor credentials must never silently satisfy platform-managed configuration.

Vendor A credentials must never be usable by Vendor B.

5. SECRET SECURITY
============================================================

Provider secrets entered through Admin/Vendor panels must:

- be encrypted at rest using the application's accepted secure mechanism;
- never be returned in plaintext by API responses;
- never be placed in frontend state unnecessarily;
- never appear in logs;
- never appear in validation errors;
- never appear in audit output;
- never appear in exception traces returned to clients;
- be redacted in UI;
- support blank-means-preserve-existing-secret editing;
- require explicit replacement to rotate;
- be owner-scoped;
- preserve immutable configuration/revision identity needed by payments.

Do not log secrets in tests.

If legacy provider storage cannot satisfy these requirements without schema
work, stop only that affected provider/configuration item and document the
minimum required correction. Continue independent work where safe.
