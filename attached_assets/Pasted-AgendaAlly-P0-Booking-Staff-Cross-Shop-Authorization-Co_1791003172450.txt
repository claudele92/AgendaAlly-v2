============================================================
CONFIRMED P0
============================================================

Affected route:

POST /api/v1/dashboard/seller/bookings/{id}/status/update

The resumed read-only audit established that an authenticated:

- moderator
- shop_manager

can satisfy the actor-side Shop middleware and the existing:

bookings.status

grant for Shop A, while the Booking service subsequently loads the requested
Booking globally by ID.

The shared assignment check has rejection branches for:

- master
- seller
- user

but an affected Staff actor that carries moderator/shop_manager without those
roles can fall through without proving that the target Booking belongs to
Shop A.

A same-country Booking belonging to Shop B can therefore reach the lifecycle
mutation path under the documented preconditions.

Do NOT execute this against existing financial data.

============================================================
1. CONTAIN THE TARGET AUTHORIZATION BOUNDARY
============================================================

The operational Seller/Staff Booking status path must establish BEFORE
lifecycle mutation that the requested Booking belongs to a Shop the
authenticated operational actor is authorized to manage.

Authorization must be TARGET-BOUND.

Actor-side possession of:

bookings.status

for some Shop is not sufficient.

The backend must establish:

authenticated operational actor
→ persisted authorized Shop relationship
→ bookings.status grant
→ requested persisted Booking
→ Booking's authoritative owning Shop
→ same authorized Shop

before Booking lifecycle mutation proceeds.

============================================================
2. USE THE EXISTING NATIVE SHOP MODEL
============================================================

Reuse existing persisted relationships and permission architecture.

Do NOT create:

- another membership table;
- another Staff role system;
- another Booking ownership field;
- another permission key.

For moderator/shop_manager operational access, use the canonical persisted
Shop relationship already established by the native application.

Use the Booking's persisted Shop attribution as the authoritative target.

Do not trust request-provided:

shop_id
seller_id
vendor_id
moderator_shop_id
branch_id
master_id

as proof that the Booking belongs to the actor's Shop.

============================================================
3. PRESERVE THE EXISTING GRANT
============================================================

Retain the existing:

bookings.status

permission requirement.

The correct contract is not:

has bookings.status somewhere
→ may update any Booking.

It must be:

authorized for THIS Booking's Shop
AND
has bookings.status for THIS Shop
→ may reach the otherwise-valid lifecycle operation.

Do not introduce a new permission merely for this containment.

============================================================
4. FAIL CLOSED
============================================================

For affected operational Staff, deny before mutation when:

- Booking does not exist;
- Booking has no Shop;
- actor has no authorized Shop;
- actor's Shop differs from Booking Shop;
- Staff membership/relationship is invalid;
- Staff relationship is pending/revoked where applicable;
- bookings.status is missing/revoked;
- target ownership is ambiguous/inconsistent.

Use the existing non-disclosing authorization/not-found contract where
appropriate.

Do not reveal whether a foreign Booking exists.

============================================================
5. DO NOT BREAK OTHER ACTOR TYPES
============================================================

The report explicitly found that this shared Booking lifecycle path has
different semantics for:

- Admin
- Customer/user
- Master/Specialist
- Seller
- moderator
- shop_manager.

Do NOT solve this by imposing Seller Shop membership on everybody.

Preserve legitimate existing behavior for:

this exact P0.

The fix should be targeted to the operational Staff/Seller Shop boundary.
