============================================================
1. DEFECT TO CONTAIN
============================================================

The current Wallet monetary amount contract accepts negative numeric values.

This creates two source-confirmed financial defects:

A. Standalone withdrawal

For x > 0, submitting -x reaches the withdrawal debit operation:

balance - (-x) = balance + x

This increases the Customer's spendable Wallet balance without funding.

B. Wallet send

A negative send amount reverses the intended economic direction:

sender is credited;
recipient is debited.

This can debit another Customer without that Customer authorizing a withdrawal.

The required invariant is therefore stronger than conservation alone:

ALL CUSTOMER-INITIATED WALLET MONEY MOVEMENT AMOUNTS MUST BE STRICTLY POSITIVE
BEFORE ANY FINANCIAL MUTATION OCCURS.

============================================================
2. MINIMUM CONTAINMENT
============================================================

Implement the smallest native-compatible correction.

At minimum, strictly positive server-side validation must apply to:

- Customer Wallet withdrawal;
- Customer Wallet send.

Reject:

- negative values;
- zero;
- signed negative decimal values;
- numeric strings representing zero or negative values;
- any other representation accepted by the current request/parser that does
  not represent a strictly positive monetary amount.

Do not rely solely on frontend validation.

Do not silently convert negative values using abs().

Do not clamp them to zero.

Do not reverse their sign.

Invalid monetary input must be REJECTED before WalletHistory creation,
Transaction creation or balance mutation.

============================================================
3. DEFENSE IN DEPTH
============================================================

Inspect the shared Wallet financial service boundary used by these operations.

Determine whether request-level positive validation alone is sufficient for the
native architecture or whether the shared service should also reject
non-positive monetary amounts.

Because this service performs the actual financial mutation, prefer a
server-authoritative invariant at the financial/service boundary as
defense-in-depth if it can be introduced without breaking legitimate native
flows.

Do not indiscriminately apply a new rule to operations whose signed values have
a legitimate internal meaning.

Trace callers first.

Document exactly where the invariant is enforced and why.

============================================================
4. DO NOT CONFUSE DIFFERENT INVARIANTS
============================================================

Preserve the previous Wallet P0 containment.

A valid positive completed transfer must still:

- debit sender exactly once;
- credit recipient exactly once;
- finalize both histories and Transactions as `paid`;
- remain non-cancellable;
- conserve total Wallet value;
- roll back both legs on failure.

The new amount validation must additionally establish:

AUTHORIZED DIRECTION OF VALUE MOVEMENT.

For a positive transfer x:

Sender: A -> A - x
Recipient: B -> B + x

Never:

Sender: A -> A + x
Recipient: B -> B - x

Conservation alone is not sufficient.
