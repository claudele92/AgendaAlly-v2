PART A — PAYMENT ARCHITECTURE AMENDMENT
============================================================

# 1. CORE PAYMENT MODEL

Implement Phase 0 and the foundational parts of Phase 1 only, incorporating the following architecture decision.

The intended AgendaAlly model is:

SUPERADMIN
defines which payment methods are available in each country
        ↓
VENDOR BUSINESS COUNTRY
determines which methods may be offered to that vendor
        ↓
AGENDAALLY / PLATFORM COLLECTION
is the DEFAULT collection mode
        ↓
CUSTOMER CHECKOUT
uses eligible platform-configured payment methods
        ↓
AGENDAALLY receives platform-collected funds
        ↓
VENDOR PAYABLE / LIABILITY
records what AgendaAlly owes the vendor
        ↓
VENDOR CONFIGURES PAYOUT METHOD
        ↓
VENDOR REQUESTS PAYOUT
        ↓
ADMIN reviews/processes payout

OPTIONALLY:

Vendor explicitly chooses vendor-direct collection
        ↓
Vendor configures an eligible supported merchant gateway
        ↓
Customer pays through vendor's own gateway/account
        ↓
AgendaAlly does NOT treat those funds as platform-held vendor liability


# 2. PLATFORM COLLECTION MUST BE THE DEFAULT

The existing `collect_via_platform` concept should remain, but its product meaning needs to be clarified.

The default for vendors should be:

“AgendaAlly Payments”

meaning AgendaAlly/platform collection.

Do not require ordinary vendors to possess merchant gateway credentials merely to participate in the marketplace.

This is especially important in markets where many small businesses may have ordinary personal/mobile-money accounts but do not have:

- MTN MoMo merchant API credentials
- Orange Money merchant API credentials
- Stripe merchant integration
- PayPal merchant integration
- other provider API credentials

Do NOT treat a normal personal mobile-money phone/account number as if it were a merchant API credential.

Do NOT invent an API integration around personal accounts.


# 3. VENDOR-DIRECT PAYMENT SHOULD BE OPTIONAL

The Vendor portal should conceptually present two collection choices:

A. AgendaAlly Payments — DEFAULT

AgendaAlly receives supported electronic payments on behalf of the vendor.

The vendor does not enter platform gateway credentials.

The vendor's proceeds become an AgendaAlly liability/payable after verified payment and applicable marketplace fees.

The vendor later requests payout using an approved payout method.

B. Use my own payment gateway — OPTIONAL

Only available where:

- Superadmin permits the method for the vendor's country,
- the provider supports vendor-direct collection,
- the vendor has the required merchant credentials,
- and the integration is actually supported.

Only in this mode should merchant credential fields appear.

Do not imply that every payment method supports vendor-direct collection.


# 4. SUPERADMIN OWNS COUNTRY PAYMENT POLICY

Superadmin must remain authoritative for:

Country
    ↓
Permitted payment methods

A vendor must never be able to activate a payment method that Superadmin has not permitted for the vendor's authoritative business country.

Vendor configuration must be an INTERSECTION of:

- globally enabled/integration-ready methods
- Superadmin country assignment
- supported transaction type
- supported currency
- supported collection mode
- valid configuration for the actual collector

Do not let the Vendor UI broaden Superadmin country policy.

Do not invent commercial/legal provider availability from provider names.

Distinguish clearly between:

ASSIGNED FOR DEVELOPMENT POLICY TESTING

and:

VERIFIED/ACTIVATED FOR REAL PAYMENTS

These are not the same.

Provider assignments must NOT:

- activate a provider globally
- set sandbox/live credentials
- imply merchant eligibility
- initiate transactions
- claim legal availability
- claim production readiness

Keep external providers inactive unless separately approved.

Cash/offline may remain available according to existing policy.

If representative assignments are necessary to test the country resolver, seed them reproducibly and label them as development policy fixtures.


# 6. COUNTRY SEED SAFETY

Any country/payment development policy seed must be:

- idempotent
- guarded for development
- rerunnable
- non-destructive

Do not:

- run `migrate:fresh`
- reset the marketplace
- replace accepted marketplace data
- create fake successful payments
- create fake payouts
- create fake refunds
- create fake wallet balances
- create fake financial transactions

Run the relevant seed twice and verify that the second run creates no duplicate policy rows.


# 7. FIX PHASE 0 SECURITY/WIRING ISSUES

Implement the bounded Phase 0 corrections identified by the audit.

Priority items include:

A. Public legacy secret exposure

`secret_id` or any equivalent credential must never be serialized through public ShopPayment resources.

Do not expose:

- API keys
- secret keys
- merchant secrets
- tokens
- subscription keys
- encrypted values
- decrypted values

Return only safe configuration metadata such as:

- configured: true/false
- enabled/status
- payment method identity
- safe non-secret labels where required

Do not inspect or print existing credential values.


B. ShopPayment ownership

Vendor show/update/delete/status operations must verify that the ShopPayment belongs to the authenticated vendor's authorized shop.

Do not allow route-model binding alone to authorize a financial configuration record.


C. Payout ownership

Seller payout operations must be actor-owned.

A vendor must not be able to:

- modify another user's payout
- replace creator ownership
- move a payout to another user
- change immutable financial ownership fields


D. Country policy authorization

Country payment policy mutations must have explicit appropriate Superadmin/global authorization or the existing correctly scoped country authorization.

Do not let ordinary vendors or unrelated country-scoped users modify platform country policy.


E. Vendor gateway status defect

Correct the existing mismatch where the status endpoint writes `active` while the actual `shop_payments` state uses `status`.

Use the existing schema unless a migration is genuinely required.

Prefer the smallest safe correction.


# 8. CHANGE THE COLLECTION CONTROL SEMANTICS

The existing Vendor “Collect via platform” switch is too implementation-oriented and potentially confusing.

Preserve backend compatibility where necessary, but improve the product semantics.

Preferred Vendor presentation:

Payment collection

● AgendaAlly Payments
  Recommended

  Accept payments using payment methods supported by
  AgendaAlly for your country. Eligible proceeds are
  available for payout according to marketplace policy.

○ Use my own payment gateway

  Connect an eligible merchant payment account supported
  in your country.

Do not automatically expose credential fields.

Only show vendor-direct gateway configuration after the vendor explicitly selects vendor-direct mode.


# 9. DO NOT CONFUSE PAYMENT METHODS WITH PAYOUT METHODS

Customer payment methods and vendor payout methods are separate concepts.

PAYMENT METHOD:
how the customer pays.

Examples could include:

- Cash
- Mobile money
- Card
- Wallet
- other supported provider rails

PAYOUT METHOD:
how AgendaAlly sends platform-collected vendor proceeds to the vendor.

Examples might eventually include:

- mobile-money payout
- bank payout
- other supported disbursement rail

Do not reuse ShopPayment merchant credentials as payout destination details unless the architecture explicitly supports that provider for both purposes.


# 10. VENDOR PAYOUT WORKFLOW

The intended future workflow is:

Customer pays through AgendaAlly
        ↓
payment is authoritatively verified
        ↓
platform fees are accounted for
        ↓
vendor share becomes vendor liability/payable
        ↓
funds become payout-eligible according to policy
        ↓
vendor requests payout
        ↓
admin approves/processes payout
        ↓
external payout completes
        ↓
liability becomes settled

However:

DO NOT IMPLEMENT THE COMPLETE PAYOUT ENGINE IN THIS PASS.

Phase 0 / foundational Phase 1 should only prepare safe architecture/contracts where necessary.

Do NOT manufacture payout completion by moving arbitrary Admin wallet balances.


# 11. PAYOUT METHOD CONFIGURATION

Audit the current Vendor payout UI/model while making the Phase 0 corrections.

The eventual Vendor experience should support:

“Payout methods”

“Customer payment collection”

For example, if later approved:

- bank account

- other payout provider

But do NOT invent unsupported payout integrations now.

Do NOT collect unnecessary sensitive financial information.

If the current model cannot safely represent a payout destination, document the required additive model rather than pretending the existing generic Payment ID is sufficient.


# 12. COUNTRY → VENDOR → CURRENCY RESOLVER FOUNDATION

    globally enabled/integration-ready methods

- Vendor configuration eligibility
- customer payment-method discovery

# 13. AUTHORITATIVE BUSINESS COUNTRY

For vendor eligibility, use the vendor/shop's actual transaction-specific business location.

Do NOT use:

- customer's selected discovery country
- selected display currency
- invitation country

as a substitute for vendor business jurisdiction.

For products and services, resolve the actual seller/business context.

If product/service locations conflict, fail clearly or use the transaction-specific location rather than silently choosing an unrelated country.
