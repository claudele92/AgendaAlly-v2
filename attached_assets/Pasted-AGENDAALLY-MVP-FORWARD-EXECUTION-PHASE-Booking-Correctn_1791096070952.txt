============================================================
3. PRIMARY OBJECTIVE
============================================================

The immediate P0 is:

BOOKING EXCLUSIVE-SLOT CORRECTNESS.

Do this first.

Do not begin another broad product assessment before resolving this gate.

Previous source review found:

1. Booking creation calculates availability before creating the booking.

2. Availability relies on ordinary reads.

3. No demonstrated resource/day admission mutex or equivalent exclusion mechanism
   was found in the traced creation path.

4. Independent Customer transactions may therefore observe the same available slot
   before either transaction commits.

5. Existing disabled/occupied-time evaluation appears capable of evaluating
   containment rather than true interval intersection.

Example:

Existing occupied/disabled interval:
09:00–10:00

Requested:
09:30–10:30

These intervals overlap.

The request must not be accepted merely because it is not completely contained
inside the existing interval.

This is currently a source-confirmed correctness concern and launch gate.
Do not exaggerate it into a proven full checkout exploit until native reproduction.

5. PHASE B — REPRODUCE THE BOOKING PROBLEM NATIVELY
============================================================

Use disposable MySQL 8/InnoDB with the selected production transaction contract.

Use the closest real application/service path possible.

Do not replace the real scheduling code with an artificial algorithm merely to
demonstrate a race.

Create focused native evidence for:

1. Exact overlap

   Existing: 09:00–10:00
   Request:  09:00–10:00

2. Left partial overlap

   Existing: 09:00–10:00
   Request:  08:30–09:30

3. Right partial overlap

   Existing: 09:00–10:00
   Request:  09:30–10:30

4. Request contained inside existing

   Existing: 09:00–11:00
   Request:  09:30–10:00

5. Request contains existing

   Existing: 09:30–10:00
   Request:  09:00–11:00

6. Adjacency

   Existing: 09:00–10:00
   Request:  10:00–11:00

Use the actual established boundary rule for adjacency.

7. Independent resources

Two different legitimate resources must not unnecessarily block one another.

8. Concurrent same-slot booking

Two independent Customers attempt the same exclusive slot concurrently.

9. Stale availability

Both Customers observe availability before either booking commits.

10. Rollback

A failed booking must not leave the slot consumed.

11. Cancellation

A legitimate cancellation must release capacity according to the existing lifecycle.

12. Reschedule

Moving a booking must not double-book the destination or incorrectly free/retain
the original slot.

13. Same-request retry/double-click

Use an existing request/idempotency identity if one exists.

Do not invent a new financial or booking identity merely for the test.

14. Closed dates

15. Disabled times

16. Working-hour boundaries

17. Duration/buffer/pause behavior where actually supported

18. Midnight/date boundary

19. Relevant timezone boundary

20. DST behavior where applicable to the actual supported timezone contract

Classify findings precisely:

- REPRODUCED DEFECT
- SOURCE-CONFIRMED RISK
- EXPECTED EXISTING BEHAVIOR
- FIXTURE/TEST ISSUE

Preserve failure receipts.

6. PHASE C — IMPLEMENT THE MINIMUM SAFE BOOKING CORRECTION
============================================================

If the defect is reproducible and the existing scheduling contract is sufficiently
defined, implement the smallest safe correction.

Required design properties:

- serialize only bookings competing for the same exclusive resource
- independent resources continue to progress independently
- perform authoritative availability/overlap revalidation inside the protected
  transaction
- do not treat the earlier availability screen as booking authority
- correctly evaluate interval intersection
- preserve existing booking identity
- preserve existing resource ownership
- preserve existing authorization
- preserve existing pricing
- preserve existing currency
- preserve existing financial allocation/custody semantics
- preserve Cash/Wallet semantics
- preserve legitimate cancellation semantics
- preserve legitimate rescheduling semantics
- preserve existing Shop/Vendor boundaries

The conceptual overlap condition will generally resemble:

requested_start < existing_end
AND
requested_end > existing_start

but do NOT blindly implement this until the actual application's rules for:

- adjacency
- buffers
- pause/additional time
- canceled bookings
- disabled periods
- timezone conversion

have been established.

Do NOT solve the problem using:

- a global booking mutex
- table-wide serialization
- role widening
- arbitrary capacity fields
- invented recurring-booking semantics
- financial repricing
- Product stock architecture
- electronic payment changes

If the minimum correct solution requires a material new scheduling schema,
new capacity model, new resource identity, changed pricing semantics, destructive
migration, or another product-level decision:

STOP BEFORE IMPLEMENTING THAT MATERIAL CHANGE.

Provide the evidence and smallest proposal for approval.

7. PHASE D — BOOKING CONCURRENCY CERTIFICATION
============================================================

After the bounded correction, rerun the native MySQL tests using genuinely
independent connections/workers where concurrency matters.

Required invariants:

1. Two Customers cannot both obtain the same exclusive appointment capacity.

2. Independent resources can book concurrently.

3. Partial overlaps are rejected.

4. Contained overlaps are rejected.

5. Containing overlaps are rejected.

6. Valid adjacency behaves according to the established contract.

7. Stale availability cannot authorize a slot that is no longer available.

8. Failed/rolled-back booking creation does not consume capacity.

9. Cancellation releases capacity exactly once and only when permitted.

10. Rescheduling transfers capacity atomically.

11. A failed reschedule leaves the original booking valid and does not consume
    the destination slot.

12. Same-request retry/double-click does not unintentionally duplicate bookings.

13. Closed/disabled periods remain authoritative.

14. Duration/buffer rules remain correct.

15. Booking admission cannot duplicate financial effects.

16. Booking failure cannot incorrectly consume Wallet authority.

17. Booking retry cannot duplicate Wallet debit.

18. Cash booking remains offline-custody accounting and does not become platform
    collection.

19. Existing frozen booking economics are not silently recalculated.

20. Independent Shop/resource activity must not be unnecessarily serialized.

Capture:

- actual database error codes
- deadlocks
- lock waits/timeouts
- rollback behavior
- retry behavior

Do not make a concurrency test green by weakening exclusivity.

A newly reproduced independent financial invariant failure is a STOP gate.

============================================================
