# ADDITIONAL SCOPE — Businesses & Specialists Discovery Redesign

Audit and improve the existing Customer storefront section currently titled:

“Businesses and people”
“Explore businesses and specialists.”

The current implementation is functional but visually inconsistent and does not use the available page width effectively.

This is a UI/UX improvement plus a bounded Specialist-profile data audit.

Do not create a competing marketplace/discovery architecture.

---

## 35. Audit the existing discovery implementation

Trace the native implementation for:

- Recommended businesses;
- Top specialists;
- business cards;
- specialist cards;
- favorites;
- “See all” navigation;
- specialist profile/detail pages;
- business/shop profile pages;
- specialist-service relationships;
- specialist category relationships;
- specialist pricing;
- service locations;
- ratings/reviews if available;
- public/private specialist visibility from the previously implemented visibility design.

Determine where every currently displayed field originates.

Do not invent frontend-only specialist data.

---

## 36. Redesign the section to fit the storefront properly

The current desktop layout leaves excessive unused horizontal space.

Improve the section so it feels like a polished AgendaAlly marketplace/discovery experience.

Preserve the existing overall storefront visual language.

The section should:

- use the available content width effectively;
- align with the primary storefront container/grid;
- have consistent horizontal margins;
- maintain clear hierarchy between businesses and specialists;
- work cleanly on large desktop, normal desktop, tablet and approximately 390px mobile;
- avoid arbitrary fixed widths that create large empty regions;
- preserve functional “See all” navigation;
- preserve favorites.

Do not simply stretch cards until they become oversized.

Choose an appropriate responsive grid/carousel treatment based on the existing design system.

---

## 37. Business cards

Improve the Recommended business cards.

Audit the current information and determine the best hierarchy.

Prefer useful information such as:

Business name
Category/business type
Short description
Location
Rating/review information if authoritative data already exists
Relevant fulfillment/booking capability if appropriate

Avoid excessive truncation such as:

“AgendaAlly...”
“Wouri Ink & Pierci...”

when sufficient card width is available.

Use controlled line clamping where necessary.

Cards within the same row should have consistent dimensions.

Images should use a consistent aspect ratio and object-fit behavior.

Do not distort uploaded business images.

## 38. Specialist cards — fix inconsistent heights

The existing Specialist cards have inconsistent heights because content such as:

48000 FCFA

wraps differently from:

9000 FCFA

This must be corrected.

All Specialist cards within the same presentation/grid should have consistent dimensions regardless of:

- name length;
- specialty length;
- price;
- currency;
- service-location text;
- rating text.

Create a deliberate card structure with stable areas for:

1. image;
2. identity;
3. specialty/domain;
4. optional business association/rating;
5. starting price;
6. service availability/location.

Use proper currency formatting.

For example:

9,000 FCFA

rather than:

9000 FCFA

and:

48,000 FCFA

must remain on one sensible price line at normal card widths.

Do not solve this by reducing text to an unreadably small font.

## 40. Prefer existing taxonomy over duplicate profile fields

Before adding a new `specialty` or `professional_domain` database field, determine whether the information can reliably be derived from existing assigned Services/Categories.

Preferred order:

1. Reuse existing explicit Specialist profession/specialty field if one exists.

2. Otherwise derive professional domain from authoritative service/category relationships if this is reliable.

3. Only propose/add a dedicated Specialist professional-domain field if existing relationships cannot represent the information properly.

Avoid maintaining duplicate taxonomy that can become inconsistent.

For example, a Specialist assigned exclusively to Barbering services should not require unrelated manually duplicated category data merely so the card can say “Barber.”

## 45. Public/private Specialist visibility

Preserve and verify the previously approved Specialist visibility semantics.

PUBLIC Specialist:
- may appear on public storefront discovery;
- may appear in Top Specialists;
- may have a public profile if supported;
- remains available during booking according to normal eligibility.

PRIVATE Specialist:
- must NOT appear in public discovery;
- must NOT appear in Top Specialists;
- must NOT expose a public Specialist profile;
- may still appear at the appropriate booking stage after the Customer chooses a service from the relevant business, according to the approved design.

This must be enforced server-side where public discovery APIs are involved.

Do not rely only on frontend filtering.
