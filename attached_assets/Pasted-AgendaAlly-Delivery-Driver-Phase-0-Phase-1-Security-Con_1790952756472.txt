Security Containment and Authoritative Vendor ↔ Driver Membership Foundation

Implement ONLY Phase 0 and Phase 1 of the approved Delivery Driver architecture.

This task is intentionally bounded.

DO NOT automatically proceed into:
- hybrid invitation/self-registration;
- new Delivery Driver Vendor UI;
- Delivery mobile-app refactoring;
- new delivery status workflows;
- proof of delivery;
- driver earnings;
- COD accounting;

Credit use is important. Reuse the existing AgendaAlly delivery architecture and run focused verification only.

==================================================
1. EXISTING ARCHITECTURE TO PRESERVE
==================================================

AgendaAlly already has useful delivery infrastructure.

Reuse rather than replace:

- User
- existing global `deliveryman` role
- existing driver settings
- existing invitation/shop relationship architecture where safe
- existing shop permissions
- `orders.deliveryman_id`
- existing seller order ownership boundaries
- existing `/api/v1/dashboard/deliveryman/...` routes where safely compatible
- existing native order status values
- existing driver notification/location infrastructure
- existing Customer order visibility
- existing Admin capabilities where intentionally authorized

Do NOT create:

- a second driver identity system;
- duplicate driver accounts;
- a second order model;
- a competing delivery subsystem;
- a second authentication system.

The desired architecture is:

User identity
    +
global delivery-driver capability/role
    +
authoritative per-shop driver membership
    +
existing Order.deliveryman_id

The global `deliveryman` role alone must NOT authorize a Vendor to assign that person to the Vendor's orders.

==================================================
2. CURRENT PROBLEMS CONFIRMED BY THE AUDIT
==================================================

The audit identified these issues.

A. Unsafe driver provisioning

Current Vendor provisioning can create a driver account while the Vendor supplies the driver's password.

Backend behavior can also permit an omitted password and generate an unsafe/predictable fallback.

Do not allow creation of insecure driver credentials.

However, do NOT implement the future contact-only invitation/self-registration workflow in this task.

Contain the unsafe behavior now without inventing a replacement onboarding flow.

If the current Vendor "Add Deliveryman" flow cannot safely operate without Vendor-created credentials, disable/hide/block that specific creation action until Phase 2 rather than preserving insecure provisioning.

Existing legitimate users/accounts must remain intact.

--------------------------------------------------

B. Driver assignment authorization

Current Vendor order assignment correctly scopes the ORDER to the authenticated Vendor's shop.

Preserve that.

But the selected driver currently only needs the global deliveryman role.

That is insufficient.

A Vendor must NEVER assign:

- another shop's driver;
- an unrelated global deliveryman;
- a suspended driver for this shop;
- an inactive account;
- a pending/unaccepted shop relationship;
- a driver whose relationship with this shop is no longer valid.

Enforce this server-side.

Frontend filtering is not authorization.

--------------------------------------------------

C. Deliveryman settings ownership

Audit the confirmed seller deliveryman-settings update path.

The existing code can locate a setting row by arbitrary ID and validate the submitted replacement user rather than first proving that the existing setting belongs to an authorized driver/shop relationship.

Correct this.

A Vendor must never read/update/delete/reassign another shop's driver settings by manipulating:

- setting ID;
- user ID;
- shop ID;
- request payload;
- UUID;
- route parameter.

Ownership must be established from the existing persisted row before mutation.

--------------------------------------------------

D. Unassigned-order driver exposure

Current driver APIs include behavior allowing delivery drivers to discover/detail/self-claim some unassigned orders without proving an authorized relationship with that shop.

Do NOT silently remove legitimate platform-dispatch behavior if that was intentional.

Instead:

1. trace the exact existing behavior;
2. distinguish:
   - Vendor-owned delivery;
   - intentional platform/global dispatch, if any;
3. ensure Vendor-owned deliveries cannot be globally enumerated or claimed by unrelated drivers;
4. preserve a platform pool only if there is an existing explicit authorization/business contract supporting it.

If the existing source cannot establish a legitimate platform-dispatch authorization boundary, fail closed for Vendor-owned delivery and document what remains unresolved.

Do not redesign dispatch in this task.

==================================================
3. PHASE 1 — AUTHORITATIVE SHOP ↔ DRIVER MEMBERSHIP
==================================================

Establish one authoritative server-side way to answer:

"Is this user currently authorized to act as a Delivery Driver for this shop?"

Do NOT use merely:

user.hasRole('deliveryman')

Do NOT rely on a singular arbitrary invitation relation.

The audit found that multiple invitation rows can exist while some existing authorization logic uses singular `User::invite()` behavior.

That is not sufficient for multi-shop authorization.

Implement/reuse the smallest clean membership architecture.

PREFERENCE:

Reuse the existing invitation/shop relationship structures if they can safely represent:

- shop_id
- user_id
- delivery-driver role/capability
- accepted relationship
- active relationship

Do not create a new table merely because it is cleaner conceptually.

However, if the existing generic invitation structure cannot safely represent an authoritative ongoing membership lifecycle, introduce the smallest additive shop-driver membership structure necessary.

Do not duplicate User, DeliveryManSetting, Shop, Order or authentication data.

==================================================
4. MEMBERSHIP RULES
==================================================

For Vendor-owned delivery, an eligible driver must satisfy ALL applicable conditions:

1. User exists.
2. User has the existing deliveryman role/capability.
3. User account is active where the existing account model requires it.
4. User has an authoritative relationship with this exact shop.
5. Relationship is accepted.
6. Relationship is active/not suspended for this shop.
7. Existing shop/staff authorization permits the acting Vendor/Staff member to manage/assign drivers.
8. Any existing approved delivery-type requirement remains satisfied.

Do not infer membership from:

- another shop;
- the user's first invitation;
- arbitrary invitation ordering;
- global deliveryman role;
- frontend list membership.

==================================================
5. MULTI-SHOP BEHAVIOR
==================================================

Do not accidentally prevent a driver from having legitimate relationships with multiple shops if the existing architecture already permits multiple invitation relationships.

Treat each shop relationship independently.

Conceptually:

Driver D
  ├── Shop A → Active
  ├── Shop B → Suspended
  └── Shop C → no relationship

Shop A may assign D.

Shop B may NOT assign D while suspended.

Shop C may NOT assign D.

Do not use global `users.active` as the mechanism for Vendor-specific suspension.

Global account disablement and per-shop driver eligibility are separate concepts.

If the current schema cannot yet represent shop-specific active/suspended membership cleanly, make the smallest additive change required for Phase 1 and document it.

==================================================
6. DRIVER LIST / PICKER AUTHORITY
==================================================

Audit the existing Vendor driver list/picker.

It must not return arbitrary global deliveryman accounts as assignable Vendor drivers.

The assignable-driver result for a Vendor shop must be derived from the authoritative membership rule.

A Vendor should eventually see only drivers such as:

- accepted;
- active for this shop;
- globally eligible;
- authorized for Vendor delivery.

Pending/unaccepted relationships must not be assignable.

Suspended relationships must not be assignable.

Drivers belonging only to other shops must not be assignable.

Do not build the future redesigned "Delivery Drivers" management page yet.

This phase concerns backend authority and existing-list containment only.

==================================================
7. ORDER ASSIGNMENT
==================================================

Harden the existing seller endpoint:

POST /api/v1/dashboard/seller/order/{id}/deliveryman

Preserve the existing own-shop order lookup.

Before persisting `orders.deliveryman_id`, verify the selected driver using the authoritative membership rule.

Also preserve applicable existing fulfillment restrictions.

Do not allow pickup/digital orders to become delivery assignments if the existing system prohibits that.

Do NOT merely repair the existing frontend payload mismatch and stop.

The audit found:

Vendor modal currently sends:

    deliveryman

while backend expects:

    deliveryman_id

The payload mismatch may be corrected ONLY AFTER the server-side membership authorization is implemented and tested.

Once the authorization boundary is secure, correct the native Vendor assignment modal to send the existing backend contract:

    deliveryman_id

Do not rename the backend field unnecessarily because future Delivery-app compatibility should preserve `deliveryman_id`.

==================================================
8. ASSIGNMENT ELIGIBILITY
==================================================

Before assignment, verify at minimum:

- acting seller/staff can manage this shop;
- order belongs to that shop;
- order is an eligible delivery order;
- selected user is a Delivery Driver;
- selected driver has accepted active membership in that shop;
- selected driver account is eligible/active;
- assignment does not bypass existing shop delivery rules.

If existing status rules already prohibit assignment at certain stages, preserve them.

If no clear status restriction currently exists, do NOT invent a complex assignment lifecycle in this phase.

Report it as a later lifecycle decision.

==================================================
9. STAFF PERMISSIONS
==================================================

Do not assume every seller-group actor may manage drivers merely because they can access Vendor routes.

Audit and reuse the existing shop permission architecture.

Existing evidence indicates:

- driver list/read uses `shop.permission:staff.view`;
- driver user creation/update/status uses `shop.permission:staff.invite`;
- assignment/settings do not have equally explicit dedicated protection.

For this phase:

- preserve Vendor owner capability;
- preserve intentionally authorized Admin capability;
- require an appropriate existing shop permission for Staff;
- do not grant Staff broader driver-management powers accidentally.

If the current permission set lacks a clean assignment permission, prefer the narrowest existing relevant permission for containment and document whether a dedicated permission should be introduced in the future UI phase.

Do not redesign the entire permission system.

==================================================
10. SHOP-SPECIFIC SUSPENSION / OFFBOARDING FOUNDATION
==================================================

Establish the distinction between:

A. global account status

and

B. driver's relationship with a specific Vendor/shop.

A Vendor must not globally deactivate a user's entire AgendaAlly account merely to stop that person from delivering for one business.

Phase 1 must establish the authoritative concept necessary to make a driver ineligible for one shop independently.

Do not yet build the final suspension/offboarding UI unless a tiny existing-control correction is necessary to prevent unsafe behavior.

Do not delete driver accounts as shop offboarding.

Do not automatically remove historical `orders.deliveryman_id` references.

==================================================
11. EXISTING ASSIGNED ORDERS
==================================================

Do not destructively rewrite historical assignments.

If a driver becomes inactive/suspended for a shop:

- they must not receive NEW assignments for that shop;
- access to currently active assignments must follow the safest existing behavior and be documented;
- completed historical deliveries must remain auditable.

Do not automatically unassign active deliveries unless the existing system already has a safe defined workflow.

If active-assignment offboarding behavior is ambiguous, report it for the later assignment-lifecycle phase.

==================================================
12. DRIVER API TENANT ISOLATION
==================================================

Audit only the driver endpoints directly affected by membership authorization.

For Vendor-owned deliveries:

A driver must not gain access merely because they have the global deliveryman role.

Require the appropriate assignment/membership boundary.

Prevent:

- Driver A opening Driver B's assigned Vendor delivery;
- unrelated Driver A claiming Shop B's Vendor delivery;
- suspended Shop A driver receiving new Shop A deliveries;
- driver with only Shop A membership acting on Shop B delivery.

Preserve legitimate Admin/platform dispatch behavior only where explicitly authorized.

Do not broadly redesign every deliveryman endpoint.

==================================================
13. DELIVERYMAN SETTINGS
==================================================

Harden existing seller deliveryman-settings operations.

For each show/update/delete or equivalent operation:

1. load the existing setting;
2. resolve its existing driver/user;
3. establish that driver's relationship with the authenticated shop;
4. establish actor permission;
5. only then permit access/mutation.

Do not authorize a foreign setting simply because the request replaces `user_id` with a local driver's ID.

Prevent ownership reassignment attacks.

==================================================
14. PROVISIONING CONTAINMENT
==================================================

Remove/disable unsafe password fallback behavior for driver provisioning.

Do not generate predictable passwords.

Do not mark contact information verified merely because a Vendor typed it unless that is backed by the existing verified-account architecture.

Because Phase 2 will implement:

Vendor
  → Invite Delivery Driver
  → email/phone invitation
  → existing user signs in OR new user registers
  → user verifies identity
  → accepts invitation
  → active shop membership

do NOT build a competing temporary onboarding architecture now.

If necessary, disable the current Vendor direct-create action until Phase 2.

Existing driver accounts must continue to work subject to the new membership authorization.
