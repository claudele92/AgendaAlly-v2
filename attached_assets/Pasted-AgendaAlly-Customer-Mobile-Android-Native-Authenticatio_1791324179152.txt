4. NATIVE SECURE STORAGE QUALIFICATION
==================================================

The principal objective is to establish whether the Phase 1 secure-token implementation behaves correctly on actual Android storage.

Qualify, where technically observable without exposing credentials:

A. SECURE TOKEN WRITE

Establish a synthetic Customer authentication/session token through a controlled test/fixture path.

Verify the application persists the bearer using the configured secure-storage adapter.

Do NOT print the token.

Use a unique synthetic sentinel/hash if evidence needs identity correlation.

--------------------------------------------------

B. NO PLAINTEXT SHARED PREFERENCES AUTHORITY

Verify that the bearer token is not stored as an ongoing plaintext SharedPreferences value.

Inspect only the specific relevant application storage boundary.

Do not dump unrelated Customer/private application data into evidence.

Do not expose actual credentials.

--------------------------------------------------

C. PROCESS RESTART PERSISTENCE

With a controlled valid synthetic/session fixture:

1. establish secure session;
2. terminate/restart the application process;
3. verify the secure bearer can be restored through the intended secure-storage path;
4. verify the app follows the current profile/session validation boundary before exposing private Customer content.

Do not claim server validity unless actually established by the controlled fixture.

--------------------------------------------------

D. LOGOUT ERASURE

Qualify successful logout/local invalidation:

1. secure bearer exists;
2. logout begins;
3. private Customer view is invalidated according to Phase 1 semantics;
4. secure bearer is removed;
5. app process is restarted;
6. previous bearer is not restored;
7. previous private Customer state is not exposed.

If remote server revocation is not exercised, clearly distinguish:

LOCAL NATIVE CREDENTIAL ERASURE VERIFIED

from:

SERVER TOKEN REVOCATION NOT EXECUTED.

Do not invent remote confirmation.

--------------------------------------------------

E. 401 INVALIDATION

Using an isolated controlled fixture:

1. establish Customer session;
2. cause/fixture a current protected 401;
3. verify local native token authority is invalidated;
4. verify Customer private navigation/state is replaced;
5. restart;
6. verify the invalidated bearer is not restored.

Do not send real financial/provider requests.

--------------------------------------------------

F. 403 PRESERVATION

Using a controlled fixture:

1. establish valid local Customer session;
2. produce a normal protected 403;
3. verify the client treats it as authorization failure;
4. verify it does NOT globally erase the Customer token/session merely because a 403 occurred.

This distinction must remain:

401 → authentication/session handling

403 → authorization failure unless an actual backend contract explicitly says otherwise.

--------------------------------------------------

G. ACCOUNT SWITCHING

Using synthetic Customer identities/session fixtures:

Customer A → logout/invalidation → Customer B

Verify:

- A's secure bearer cannot be reused;
- A's private cached profile/Wallet/account state is not displayed to B;
- stale A responses cannot update B;
- B establishes a separate current session;
- restarting the app does not resurrect A.

Do not use real Customer credentials.

--------------------------------------------------

H. LEGACY PLAINTEXT TOKEN DISCARD

If safely testable on the native runtime:

1. create a synthetic legacy SharedPreferences bearer in the old key location;
2. initialize the current application/session layer;
3. verify the legacy token is discarded rather than promoted to active authority;
4. verify legacy plaintext key removal;
5. verify Customer/account cache cleanup required by Phase 1;
6. verify reauthentication is required.

Do not use a real historical token.

--------------------------------------------------

I. CLEANUP FAILURE / RECOVERY

Phase 1 introduced blocked recovery when durable local cleanup cannot be confirmed.

Where a controlled fault can legitimately be injected without corrupting the environment:

- simulate secure deletion/storage failure;
- verify the application does not present logout as successfully completed;
- verify private Customer access remains blocked;
- verify retry/recovery behavior;
- verify the application does not silently reactivate an uncertain token.

Do not claim actual Android Keystore corruption if only an adapter-level fault is injected.

Clearly label the evidence level.

2. no continuing plaintext SharedPreferences bearer authority;

8. account switching does not expose/reuse the previous Customer session;

9. legacy plaintext token handling behaves according to the Phase 1 design where safely testable;
