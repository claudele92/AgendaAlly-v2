AgendaAlly — Phase 3B-1
Durable MTN Request Identity & Unknown-Outcome Recovery

The Phase 3B MTN Cameroon/XAF certification stopped under its required
material-contract deviation rule.

The stop finding is accepted.

AUTHORITATIVE FINDING
=====================

MTN RequestToPay is asynchronous and status reconciliation uses the original
request reference.

AgendaAlly currently sends RequestToPay BEFORE durably saving that provider
reference in PaymentProcess.

Therefore this sequence is possible:

1. AgendaAlly generates MTN request reference R1.
2. AgendaAlly sends RequestToPay(R1).
3. MTN accepts or may have accepted R1.
4. AgendaAlly times out OR the subsequent local persistence fails.
5. AgendaAlly has no durable R1 in its normal reconciliation state.
6. A later retry may generate R2 instead of reconciling R1.

No duplicate Customer debit was demonstrated.

This is an external-payment-identity / unknown-outcome recovery defect, not
evidence that duplicate collection has already occurred.

MTN remains disabled.

Official MTN public sandbox documentation currently identified in Phase 3B
uses EUR. Fixing this identity defect MUST NOT be represented as Cameroon/XAF
certification.

============================================================
1. AUTHORIZED OBJECTIVE
============================================================

Implement and verify the MINIMUM NON-ACTIVATING correction required to ensure:

ONE AGENDAALLY MTN PAYMENT ATTEMPT
↔
ONE DURABLE IMMUTABLE MTN REQUEST REFERENCE

and ensure an uncertain RequestToPay outcome is recoverable through that same
reference.

The required lifecycle should conceptually be:

canonical payment attempt established
→ MTN reference generated
→ reference durably persisted
→ persistence committed
→ RequestToPay dispatched using exactly that reference
→ outcome classified
→ same reference reconciled until authoritative terminal state.

Do not create another provider reference merely because:

- HTTP response timed out;
- connection failed after dispatch may have occurred;
- process crashed;
- frontend retried;
- Customer refreshed;
- callback was delayed;
- provider result is temporarily unknown.

============================================================
4. DURABILITY INVARIANT
============================================================

No MTN RequestToPay may be dispatched unless its provider request reference has
already been durably persisted.

The durable record must be committed before external dispatch.

Do NOT perform:

database transaction open
→ external MTN network request
→ database commit

if doing so leaves the provider call dependent on an uncommitted local
identity.

External network I/O must not be relied upon as part of database atomicity.

============================================================
5. IMMUTABLE PROVIDER REFERENCE
============================================================

Once assigned to an MTN payment attempt, the provider request reference must be
immutable for that attempt.

Retry must not replace it.

Reconciliation must use it.

Frontend retry must resolve to it.

Replacement Transaction handling must not silently create another MTN payment
identity for the same existing attempt.

If the current schema cannot safely enforce the necessary identity:

STOP BEFORE MIGRATION.

Report:

MTN PAYMENT IDENTITY SCHEMA CHANGE REQUIRED

with the minimum proposal.

Do not hide immutable identity in mutable settings or request payloads.

============================================================
6. PRE-DISPATCH STATE
============================================================

The local lifecycle must distinguish an attempt whose identity exists before
dispatch.

Use existing states if they can represent this unambiguously.

Do not invent misleading financial meaning.

A durably persisted MTN attempt before RequestToPay does NOT mean:

paid
funded
provider accepted
Customer debited.

It means only that AgendaAlly has reserved the durable external request
identity required for safe dispatch/recovery.

============================================================
7. DISPATCH OUTCOME MODEL
============================================================

After RequestToPay dispatch, distinguish at minimum:

A. DEFINITELY NOT DISPATCHED

Only when the application can prove the provider request was never sent.

B. DISPATCHED / RESPONSE KNOWN

The provider interaction returned enough evidence to classify the next state.

C. DISPATCH OUTCOME UNKNOWN

The request may have reached MTN but AgendaAlly cannot safely know the outcome.

Timeout, connection interruption after possible transmission, process failure,
or ambiguous transport result must NOT automatically become definitive
payment failure.

============================================================
8. UNKNOWN OUTCOME
============================================================

UNKNOWN is a first-class recovery condition.

For an unknown RequestToPay outcome:

- retain the original MTN reference;
- do not generate another reference;
- do not mark paid;
- do not create confirmed canonical funding;
- do not create commission/payable;
- do not assume failure merely to permit another payment attempt;
- reconcile the original reference.

If reconciliation returns pending:

remain recoverable/pending.

If reconciliation returns authoritative success:

settle exactly once through the accepted canonical accounting path.

If reconciliation returns authoritative failure:

transition according to the accepted failure/finality rules.

If reconciliation itself is unavailable:

remain unresolved/fail closed.

============================================================
9. SAFE RETRY
============================================================

Define retry semantics explicitly.

TRANSPORT / UI RETRY OF SAME PAYMENT ATTEMPT:

must reuse the existing durable MTN identity or reconcile it.

It must not create a new RequestToPay merely because the previous HTTP response
was lost.

A genuinely NEW payment attempt may receive a new MTN reference only after the
previous attempt is authoritatively terminal in a state that permits another
attempt under the accepted checkout rules.

Do not invent a new checkout_key merely to escape an unresolved provider
attempt.

============================================================
10. CRASH RECOVERY
============================================================

Verify recovery for:

A.
reference persisted
→ crash before dispatch.

B.
reference persisted
→ RequestToPay dispatched
→ crash before response processing.

C.
reference persisted
→ MTN accepts
→ local response handling crashes.

D.
reference persisted
→ timeout
→ later reconciliation success.

E.
reference persisted
→ timeout
→ later reconciliation failure.

The system must preserve enough state to recover without inventing another
provider identity.

============================================================
11. UNSENT PERSISTED ATTEMPT
============================================================

Carefully distinguish:

REFERENCE PERSISTED BUT REQUEST DEFINITELY NEVER DISPATCHED

from:

REQUEST MAY HAVE BEEN DISPATCHED.

If the existing implementation cannot prove this distinction reliably, prefer
the conservative UNKNOWN/reconciliation path.

Do not resend an ambiguous attempt merely because no success response exists.

============================================================
12. RECONCILIATION
============================================================

The normal MTN reconciliation path must be able to start from the durable local
attempt and recover using the original provider reference.

Verify:

- correct provider;
- correct merchant owner;
- correct Shop;
- correct payable;
- correct amount;
- correct currency;
- correct canonical checkout/payment identity.

Reconciliation must not accept a provider reference supplied only by the
Customer as authoritative identity.

============================================================
13. AUTHORITATIVE PAYMENT BOUNDARY
============================================================

Do not change the accepted MTN authority model.

RequestToPay initiation is NOT payment proof.

A persisted provider reference is NOT payment proof.

Dispatch success is NOT payment proof.

HTTP success alone is NOT payment proof.

Frontend state is NOT payment proof.

Only the accepted authoritative MTN verification/reconciliation boundary may
confirm funding.

============================================================
14. CANONICAL ACCOUNTING
============================================================

Do not redesign Phase 2 accounting.

Before authoritative success:

confirmed contribution = none
commission effect = none
Vendor payable effect = none.

After authoritative success:

invoke the existing canonical accounting path exactly once.

Duplicate reconciliation of the same successful MTN payment must remain
idempotent.
