1. P0 being remediated

The completed audit established this source-confirmed defect:

An authorized Seller can transition the same Product Order into "delivered", move it to another accepted non-canceled status, and later transition it to "delivered" again.

Each transition into "delivered" can execute:

"OrderStatusUpdateService::adminWalletTopUp"

which creates another paid Wallet top-up for the first Admin Wallet using the persisted gross Order total.

There is no durable per-Order financial settlement marker or funding claim preventing the same Order from producing the gross Wallet credit more than once.

Therefore:

"delivered → other allowed state → delivered"

can create another positive internal Wallet credit without another Customer payment.

Cashback may also repeat where its eligibility conditions apply. Treat that as part of the same fulfillment-finality investigation if it is driven by the same transition.

This finding is SOURCE-CONFIRMED / UNCONTAINED. It was deliberately not exploited during the read-only audit.

Primary source anchors from the completed audit:

- "app/Services/OrderService/OrderStatusUpdateService.php:50–98"
- "app/Services/OrderService/OrderStatusUpdateService.php:179–199"
- "app/Services/OrderService/OrderStatusUpdateService.php:239–256"
- Seller "OrderController::orderStatusUpdate"
- "app/Http/Requests/Order/StatusUpdateRequest.php"
- "routes/api.php:725"

Use function names as authoritative anchors if line numbers have shifted.

2. Objective

Implement the minimum durable financial-finality correction necessary to guarantee:

«One Order's fulfillment can produce each fulfillment-triggered financial entitlement/effect at most once unless there is a separately funded and explicitly modeled financial event authorizing another effect.»

At minimum, the gross Admin Wallet credit associated with fulfillment must not be repeatable by cycling Order statuses.

Do not merely hide the problem in the frontend.

Do not rely only on an identical-status check.

Do not rely only on request timing.

Do not rely only on the current Order status.

Do not rely only on application-level "exists()" followed by an unprotected write if concurrent requests could both pass.

The once-only boundary must be durable and server-authoritative.

4. Determine the correct once-only boundary

Before implementation, explicitly answer:

A. What financial event is actually being represented by "adminWalletTopUp"?

Determine from native source whether it is intended to represent:

- platform collection,
- Vendor entitlement,
- settlement,
- internal bookkeeping,
- legacy accounting,
- or another concept.

The completed audit already established that this legacy gross Admin Wallet credit must not be treated as proof of actual provider or Cash custody.

Do not invent a new accounting meaning during containment.

B. What existing durable identity can safely establish once-only fulfillment?

Prefer an existing native durable record/relationship if one already provides the correct financial identity.

Examples to investigate, not assumptions:

- Order ID + financial effect type;
- existing Transaction relationship;
- WalletHistory relationship;
- ledger entry;
- settlement/finality field already present on Order or a related native record.

Do not add a schema migration unless the existing model cannot provide a correct durable claim.

If a schema change is genuinely necessary, stop before implementing it and report why the current schema cannot safely express once-only settlement.

C. What should happen when an already financially settled Order re-enters "delivered"?

The Order lifecycle and the financial settlement lifecycle do not necessarily have to be identical.

If business rules legitimately permit leaving and re-entering "delivered", the financial effect must still remain once-only.

If source establishes that "delivered" is supposed to be terminal, a transition restriction may be appropriate, but do not assume that without tracing all legitimate callers.

5. Atomicity requirement

The once-only financial claim and its associated financial mutations must share an appropriate SQL transaction boundary.

The correction must prevent:

Sequential replay

"delivered → other status → delivered"

must not create another gross Wallet credit.

Stale-model replay

Two service instances operating from stale Order state must not independently settle the same fulfillment.

Concurrent settlement

Two concurrent attempts to establish the same fulfillment settlement must not both create financial effects.

Use native database locking/uniqueness/conditional-update mechanisms appropriate to the existing architecture.

Do not claim production concurrency certification from SQLite testing.

A controlled two-connection test may establish the intended SQL claim behavior, but production concurrency must remain explicitly uncertified unless separately approved and tested on the production database technology.

---

6. Failure atomicity

If the fulfillment financial claim is acquired but a required financial operation fails:

- do not leave the Order falsely marked financially settled;
- do not leave only part of the required financial effects committed;
- do not allow a failed partial attempt to permanently block a legitimate retry;
- do not silently ignore false service results.

Explicitly test both thrown exceptions and native service methods that may return failure without throwing.

The financial claim and required SQL effects must commit or roll back consistently.

9. Required replay/finality tests

Create focused isolated tests proving at least:

1. First legitimate transition into "delivered" performs the intended financial effect exactly once.
2. Repeating "delivered" directly cannot duplicate it.
3. "delivered → another permitted status → delivered" cannot duplicate it.
4. Multiple cycles cannot duplicate it.
5. A stale Order/service instance cannot duplicate it.
6. Duplicate requests cannot produce multiple Admin Wallet credits.
7. Duplicate WalletHistory records are not created for the same fulfillment effect.
8. Duplicate Transactions are not created for the same fulfillment effect.
9. Cashback cannot repeat through the same replay if it belongs to this settlement boundary.
10. A failed required Wallet operation rolls back the financial claim/effects.
11. An exception during settlement rolls everything back.
12. A legitimate retry after a rolled-back failed attempt can succeed exactly once.
13. Existing legitimate first-time fulfillment still works.
14. Existing authorization rules remain intact.
15. Existing accepted payment/refund/Wallet containment tests relevant to touched shared code still pass.

If the existing financial operation returns "false" rather than throwing, include that case explicitly.
