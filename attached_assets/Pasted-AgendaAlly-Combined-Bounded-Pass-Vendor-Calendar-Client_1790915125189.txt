==================================================
PART A — VENDOR CALENDAR CUSTOMER / CLIENT WORKFLOW
==================================================

I found an incorrect behavior in the Admin/Vendor Business portal.

When a Vendor creates/adds a booking from the business calendar, the Customer field currently discovers records such as Staff and legacy Master/Specialist users.

That is incorrect.

For a business-created appointment:

CUSTOMER / CLIENT
= the person receiving/purchasing the service.

SPECIALIST / STAFF
= the business worker performing the service.

These must remain separate concepts.

--------------------------------------------------
A1. AUDIT ONLY WHAT IS NECESSARY
--------------------------------------------------

Trace only the existing code required to understand and fix:

- Calendar → Add/Create Booking
- Customer/client selector
- Customer search endpoint/query
- Service selector
- Specialist/Staff selector
- Shop/branch context
- Booking creation endpoint
- Existing customer/client models
- Existing customer creation mechanisms
- Laravel validation/authorization
- React Admin/Vendor form
- Shared API contracts if relevant

Do not perform another broad application audit.

Determine the exact cause of Staff/Master/Specialist records appearing in Customer discovery and fix the underlying boundary.

--------------------------------------------------
A2. CUSTOMER SELECTOR
--------------------------------------------------

The Customer field must return legitimate customer/client records for the business workflow.

It must NOT return someone merely because that person exists in the general user table.

Exclude inappropriate identities such as:

- Staff
- Specialists
- legacy Masters
- Vendor/business-owner accounts acting only in those roles
- Admins
- Country Managers
- unrelated internal/system accounts
- unauthorized users from other businesses

Do NOT implement this as:

fetch all users
→ filter them in React.

The backend customer-search query/endpoint must enforce the correct domain boundary.

Preserve existing shop/branch/tenant/privacy boundaries.

--------------------------------------------------
A3. EXISTING CLIENT SEARCH
--------------------------------------------------

The Vendor should be able to search legitimate existing clients naturally.

Where supported by the current model, allow appropriate search using:

- Name
- Phone
- Email

Do not expose unnecessary customer information.

The UI should make the intent obvious:

Customer

[ Search existing clients... ]

Search results should contain enough information to distinguish customers without exposing unnecessary account details.

--------------------------------------------------
A4. ADD NEW CLIENT
--------------------------------------------------

Add a clear action inside the booking workflow:

+ Add new client

or:

+ New customer

Use whichever terminology best matches existing AgendaAlly terminology.

The Vendor should not need to leave the calendar, create the customer elsewhere, return to the calendar and restart the booking.

First inspect whether AgendaAlly already has a legitimate customer/client creation mechanism.

REUSE existing architecture where possible.

Do not create a duplicate customer model unnecessarily.

--------------------------------------------------
A5. REGISTERED USER VS WALK-IN CLIENT
--------------------------------------------------

This distinction is important.

A business may need to manually book an appointment for someone who does NOT have an AgendaAlly login account.

Determine whether the current architecture supports:

A. registered AgendaAlly customers only;

B. business-local/walk-in client records;

C. both.

Do not guess.

If business-local/walk-in clients are already supported, use that mechanism.

If they are not supported, implement only the smallest clean extension necessary to represent a legitimate manual-booking client.

Do NOT fabricate:

- email addresses
- passwords
- OTPs
- social-login identities
- fake customer registrations
- fake verified accounts

just to satisfy a registration model.

Entering a client's information for a business-created appointment must not automatically imply that the person registered for AgendaAlly unless that lifecycle is genuinely supported.

--------------------------------------------------
A6. NEW CLIENT FORM
--------------------------------------------------

Use only fields legitimately required by the existing model/workflow.

Likely examples may include:

- First name
- Last name
- Phone
- Email

but inspect actual validation first.

Do not arbitrarily require every field.

If the architecture legitimately supports a walk-in with name + phone, do not force email simply because the public registration screen requires one.

After successful creation, immediately select the new client in the booking form.

Do not require a page reload.

--------------------------------------------------
A7. DUPLICATE CLIENT HANDLING
--------------------------------------------------

Audit existing uniqueness rules.

Where safe and supported, normalize phone/email and avoid creating duplicate client records.

If the entered phone/email belongs to an appropriate existing client that this Vendor is authorized to discover, offer/use that client instead.

Do NOT leak the existence of users the Vendor is not authorized to discover.

--------------------------------------------------
A8. SPECIALIST / STAFF REMAINS SEPARATE
--------------------------------------------------

Keep Specialist/Staff selection separate from Customer.

The Specialist/Staff selector should return only eligible workers for the selected:

- business/shop
- branch/location
- service

according to existing AgendaAlly scheduling and authorization rules.

Do not put customers into this selector.

Do not broaden Staff visibility while fixing Customer discovery.

Use “Specialist” or “Staff” in new UI.

Do not reintroduce legacy “Master” terminology.

--------------------------------------------------
A9. SERVICE → SPECIALIST RELATIONSHIP
--------------------------------------------------

If AgendaAlly already models which Specialists/Staff can perform a service, preserve that relationship.

The conceptual manual-booking flow should be:

Customer
   ↓
Service
   ↓
Eligible Specialist / Staff
   ↓
Date / Time
   ↓
Create Booking

Do not invent another scheduling engine.

Preserve existing availability behavior.

--------------------------------------------------
A10. SERVER-SIDE ENFORCEMENT
--------------------------------------------------

Booking creation must validate server-side that:

- the selected customer/client is legitimate for this workflow;
- the selected Specialist/Staff is eligible;
- the actor can manage the selected shop/branch;
- forged IDs cannot bypass those restrictions.

Specifically verify that changing request IDs cannot:

- use Staff as Customer;
- use another business's protected client;
- use another business's Specialist;
- use an unauthorized branch/shop.

Preserve legitimate Admin behavior separately from Vendor behavior.

==================================================

The previous Stories audit already identified an ownership/tenant-isolation concern.

Do NOT redo the entire Stories audit.

Fix it now before implementing the Stories visual improvement.

A Vendor must never be able to open private management data for, edit, update, delete, publish/unpublish, replace media for, or otherwise manage another business/shop's Story by manipulating:

- ID
- UUID
- route
- request parameter
- shop ID
- payload
- media identifier

--------------------------------------------------
B1. SERVER-SIDE STORY OWNERSHIP
--------------------------------------------------

Audit only the relevant existing Story:

- routes
- controller
- service
- repository
- requests
- policies/middleware
- Vendor UI calls

Bind every Vendor Story management operation to the authenticated Vendor's authorized business/shop.

Do not rely on frontend filtering.

--------------------------------------------------
B2. COVER EXISTING OPERATIONS
--------------------------------------------------

Apply ownership enforcement wherever applicable to:

- list/paginate
- show/open/edit
- create
- update
- delete
- status changes
- visibility changes
- publish/unpublish
- media replacement
- media removal
- other existing Story mutations

--------------------------------------------------
B3. STAFF AND ADMIN
--------------------------------------------------

If Staff can legitimately manage Stories, preserve the existing permission model but restrict Staff to authorized shop/business scope.

Preserve legitimate Admin/Superadmin behavior where broader access is intentionally authorized.

Do not weaken country/shop/role boundaries.

--------------------------------------------------
B4. STORY MEDIA OWNERSHIP
--------------------------------------------------

Check whether Story media can be removed/replaced using a forged Story or media identifier.

A Vendor must not be able to alter another business's Story media independently of Story ownership.

Apply the same server-side ownership boundary.
