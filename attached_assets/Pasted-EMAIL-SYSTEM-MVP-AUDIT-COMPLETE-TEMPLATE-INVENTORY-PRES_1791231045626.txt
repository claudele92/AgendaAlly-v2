EMAIL SYSTEM MVP AUDIT — COMPLETE TEMPLATE INVENTORY, PRESENTATION CONSISTENCY, MISSING-TEMPLATE PROPOSAL, AND READINESS IMPACT

Context / accepted evidence

AgendaAlly SMTP transport has already been successfully tested end-to-end from the existing normal Admin preview.

The Admin Test Email:
- successfully connected through the configured Zoho SMTP provider;
- displayed “Test email sent successfully”;
- was actually received in Gmail at the intended recipient;
- used the current encrypted SMTP credential;
- used verified TLS;
- successfully rendered the corrected AgendaAlly logo;
- successfully rendered the corrected Instagram, Facebook and LinkedIn icons;
- rendered the footer correctly in Gmail.

The previous SMTP failure was caused by an issue with the Zoho account/configuration and has been resolved.

The original email-presentation defects were:
- logo URL pointed to localhost and therefore could not be fetched by Gmail;
- social icons were literal text labels;
- social links could become malformed by prepending https:// to URLs that already contained a scheme.

Those presentation defects have already been corrected using owned/local email-safe assets, CID embedding and normalized links.

Therefore:

SMTP TRANSPORT: VERIFIED
ACTUAL GMAIL DELIVERY: VERIFIED
CORRECTED ADMIN TEST EMAIL PRESENTATION IN GMAIL: VERIFIED

Do NOT repeat the generic Admin SMTP Test Email.

The purpose of this task is now to audit the complete AgendaAlly email system, verify presentation consistency locally, identify missing MVP transactional emails, and determine exactly what remains necessary for communications/readiness gates C1 and O4.

This is primarily an AUDIT + LOCAL VERIFICATION + PROPOSAL task.

Do not implement new email workflows without approval.

Do not send any email during this task.

9. LOCAL CLIENT EMAIL SEMANTICS
==================================================

Audit how the new local-client model should interact with email.

Remember:

A local client is a Shop-scoped directory record.

It does NOT automatically have a platform User account.

It must NOT:

- receive platform credentials;
- be told that an AgendaAlly account was created;
- receive account verification intended for platform Users;
- be automatically linked to a global account merely because an email matches.

Determine whether a local client with a valid email address can safely receive:

- booking confirmation;
- reschedule notice;
- cancellation notice;
- reminder.

If the existing contract does not safely support this, classify it as proposed/deferred.

Do not invent automatic account linking.

26. IMPORTANT DECISION RULE
==================================================

Do not treat “more email templates” as automatically improving MVP readiness.

The objective is:

correct emails
+
authoritative triggers
+
secure generation
+
consistent presentation
+
appropriate recipients
+
verified critical journeys

—not the largest possible number of notifications.

If AgendaAlly already has enough email functionality for MVP, say so.

If an email is unnecessary for MVP, classify it as optional/deferred.

If a proposed email depends on an unverified payment/refund/payout/accounting state, defer it.

If a template exists but the application has no authoritative trigger, do not call it ready.
