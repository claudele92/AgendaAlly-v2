==================================================

I found a potentially serious issue:

In the Shop/Vendor portal calendar, a Vendor can currently see Specialists/Masters belonging to other Vendors/Shops.

Treat this initially as a potential tenant-isolation/security defect, not simply a UI filtering issue.

Audit the complete data path:

- Calendar Specialist/Master filters

- Booking create/edit forms
- Calendar event queries
- Specialist lookup/search endpoints
- Service → Specialist assignment queries

- Backend controllers/services/repositories

Establish the authoritative Shop/Specialist ownership model from source before changing behavior.

A Vendor operating Shop A must NOT be able to enumerate, select, assign or use a Specialist belonging exclusively to Shop B by manipulating the UI, query parameters, request body or IDs.

DO NOT fix this only by hiding Specialists in the frontend.

Backend/API query scoping and authorization must enforce the boundary.

At the same time, preserve legitimate multi-Shop Specialist assignments. If a Specialist has valid accepted assignments to multiple Shops, those relationships must continue working according to the existing authorization model.

Test at minimum:

POSITIVE:
Shop A can see and use Specialists legitimately assigned to Shop A.

NEGATIVE:
Shop A cannot enumerate or use a Specialist belonging only to Shop B, including through a crafted direct API request.

If unauthorized cross-Shop access is confirmed, classify it appropriately in the readiness/security report and fix the security defect before considering the calendar production-ready.
