==================================================
1. AUTHORITATIVE FINDINGS TO CLOSE
==================================================

P0-01 — SENSITIVE AUTH/API TRANSPORT AND LOGGING

The audit established:

- login currently submits credentials using URL query parameters;
- the shared HTTP client installs request/header/body/response logging without a sufficient release/sensitive-data guard;
- WebView/deep-link helpers also contain URL logging risks;
- credentials, bearer tokens, sensitive URLs or sensitive response content must not be exposed through application logs.

Primary audit references include:

M/lib/infrastructure/repository/auth_repository.dart

M/lib/infrastructure/service/http_service.dart

and related interceptors/helpers identified by the audit.

Required outcome:

Authentication secrets must use the current backend-supported safe request-body contract where applicable.

Passwords, OTPs, bearer tokens, authorization headers, sensitive query values and equivalent authentication material must not be exposed through logs.

Do not merely hide one login log statement while leaving equivalent disclosure paths active.

--------------------------------------------------

P0-02 — BEARER TOKEN STORED IN SHAREDPREFERENCES

The audit established that bearer tokens are persisted in ordinary SharedPreferences.

Primary audit reference:

M/lib/infrastructure/local_storage/local_storage.dart

Required outcome:

Bearer/authentication tokens must use appropriate secure platform storage rather than ordinary SharedPreferences.

Do not move ordinary non-sensitive application preferences into secure storage unnecessarily.

Preserve the existing application's useful preference/cache architecture where safe.

--------------------------------------------------

DIRECTLY RELATED SESSION FOUNDATION

The audit also established:

- logout navigation occurs without properly awaiting/handling authoritative logout;
- local credentials are cleared only after successful server logout;
- an offline/timeout logout can leave old token/profile state on-device after UI navigation;
- unauthorized/expired-session handling is not centrally coordinated;
- account-specific cached/in-memory state may survive session/account transitions;
- Firebase or other identity/session state must not accidentally survive an AgendaAlly Customer logout where it is part of the authenticated Customer identity path.

This campaign MAY repair these directly related session-lifetime problems because they are necessary to close the authentication/confidentiality boundary coherently.

Do not broaden the task into unrelated application-state refactoring.

==================================================
6. SECURE TOKEN STORAGE
==================================================

Replace bearer-token persistence through ordinary SharedPreferences with an appropriate Flutter secure-storage abstraction backed by platform secure facilities.

The design should support Android/iOS appropriately.

Requirements:

- bearer token must not remain in ordinary SharedPreferences after successful migration;
- new tokens must be written only to the secure token store;
- reads must use the secure token store;
- logout/session invalidation must remove the secure token;
- failed/expired/revoked sessions must not leave a usable token behind;
- account switching must not expose a previous Customer token;
- avoid duplicate token authorities.

Do not store the token simultaneously in secure storage and SharedPreferences as permanent authorities.

If a migration path from legacy SharedPreferences is necessary, make it bounded and one-way.

A safe migration may:

1. detect an existing legacy token;
2. migrate it to secure storage if appropriate;
3. remove the SharedPreferences token;
4. thereafter use secure storage as the only persistent token authority.

Do not expose the legacy token in logs.

Do not make unsupported assumptions about backups/keychain behavior.

Document the actual secure-storage package/configuration and platform behavior used.

Do not move harmless UI preferences into secure storage simply for consistency.

==================================================
7. COORDINATED SESSION LIFETIME
==================================================

Repair the session boundary coherently.

A Customer logout must not be represented as complete merely because the UI navigated to Login.

Design the client so it safely handles:

A. successful server logout;

B. logout timeout/network failure;

C. already-invalid/revoked token;

D. server 401;

E. server 403;

F. app restart with valid local session;

G. app restart with invalid/expired/revoked session;

H. account switching.

Distinguish authentication failure from authorization failure:

401 generally indicates authentication/session handling.

403 generally indicates authenticated-but-forbidden behavior and must not automatically be treated as logout unless the actual backend contract says otherwise.

Do not globally convert every 403 into session destruction.

Implement centralized handling where appropriate rather than duplicating inconsistent behavior across screens.

==================================================
8. LOGOUT SECURITY SEMANTICS
==================================================

The logout implementation must explicitly define and test what happens when the server cannot be reached.

The client must not leave the user visually logged out while silently retaining reusable local authentication credentials indefinitely.

At the same time, do not falsely claim the server session/token was revoked if the server logout request was not confirmed.

Preserve this distinction:

LOCAL SESSION/CREDENTIAL CLEARING

is not identical to:

SERVER TOKEN REVOCATION CONFIRMED.

If server logout is uncertain because of network loss/timeout:

- clear or securely invalidate local Customer authentication state as appropriate;
- prevent continued local authenticated use;
- do not claim server revocation was confirmed;
- handle subsequent authentication safely.

Use the actual Sanctum/backend behavior when designing this.

Do not invent a refresh-token system.
