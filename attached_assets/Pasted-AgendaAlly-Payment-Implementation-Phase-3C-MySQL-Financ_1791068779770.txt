MySQL Financial Concurrency & Conservation Certification

The completed payment architecture, containment work, Phase 2 accounting,
Phase 3A provider-state separation, and the latest payment-system completion
milestone are accepted within their documented scopes.

The latest milestone established:

- Durable provider/payment identity is implemented.
- Provider attempts exist before dispatch.
- Original merchant/configuration revisions are retained.
- Product and Booking use canonical accounting for supported paths.
- Refund orchestration exists for supported provider adapters.
- Commission receivable settlement exists.

============================================================
1. PRIMARY OBJECTIVE
============================================================

Certify that AgendaAlly's accepted financial invariants remain correct under
MySQL/InnoDB transaction, row-locking, uniqueness and concurrent-request
semantics.

The primary question is:

CAN TWO OR MORE CONCURRENT REQUESTS CAUSE A FINANCIAL EFFECT TO EXCEED THE
MONEY, LIABILITY, REFUNDABLE AMOUNT, RECEIVABLE OR PAYMENT EVIDENCE ACTUALLY
AVAILABLE?

The answer must be established using an isolated disposable MySQL database
with synthetic financial fixtures.

Do not use production.

6. CONSERVATION INVARIANT
============================================================

For every relevant concurrent financial operation establish:

TOTAL ECONOMIC EFFECT
<=
AUTHORITATIVELY AVAILABLE VALUE.

Depending on the operation, "available value" means:

- refundable amount;
- confirmed platform-held contribution;
- unsettled Vendor payable;
- outstanding commission receivable;
- Wallet balance;
- reserved-but-not-finalized amount;
- provider evidence that has not already produced its canonical effect.

Concurrency must never manufacture additional value.

============================================================
7. REFUND RESERVATION
============================================================

This is a critical test.

Given a payment with a known refundable amount, create competing refund
requests using independent MySQL connections.

Test at minimum:

A. Two refunds individually valid but jointly excessive.

Example:

refundable = 100

Concurrent requests:

refund A = 70
refund B = 70

At most 100 total may become reserved/finalized.

Both must never successfully reserve 140.

B. Exact concurrent exhaustion.

refundable = 100

refund A = 60
refund B = 40

Both may succeed only if the final state is exactly 100 and all accounting
effects remain correct.

C. Same refund replay.

Two workers attempt the same refund identity/effect.

Only one economic reservation/effect may exist.

D. Existing partial refund.

gross = 100
already refunded = 30

Concurrent new refund attempts must respect remaining refundable = 70.

Verify locking and calculations occur against authoritative persisted state,
not stale application models.

52. SUCCESS CRITERIA
============================================================

Do not call this phase successful merely because tests run on MySQL.

Success means the accepted financial invariants survive actual independent
MySQL/InnoDB concurrent transactions:

AVAILABLE MONEY CANNOT BE SPENT/REFUNDED/RESERVED TWICE.

ONE PROVIDER PAYMENT CANNOT CREATE TWO ECONOMIC PAYMENTS.

ONE ECONOMIC PAYMENT CANNOT CREATE TWO COMMISSIONS.

ONE ECONOMIC PAYMENT CANNOT CREATE TWO VENDOR LIABILITIES.

ONE WALLET BALANCE CANNOT FUND MORE VALUE THAN IT CONTAINS.

ONE REFUNDABLE BALANCE CANNOT REFUND MORE THAN IT CONTAINS.

ONE VENDOR PAYABLE CANNOT BE RESERVED BEYOND ITS AVAILABLE LIABILITY.

AN INTERNAL PAYOUT RESERVATION CANNOT PRETEND AN EXTERNAL PAYOUT OCCURRED.

A valid result may be:

If so, report exactly why rather than weakening the invariant.
