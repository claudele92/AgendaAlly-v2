- exact reservation remainders passed;
- independent-allocation progress passed;

- no over-credit was observed.

The shared new failure was:

CONCURRENT IDENTICAL-RECEIPT CONTRIBUTION CONFIRMATION.

The owner committed successfully.

The waiting contender then rejected with:

`Terminal allocation/contribution cannot accept funding.`

The contender reused a pending contribution/context object that had been
hydrated before waiting on the authoritative parent lock.

After the lock wait completed, the database contained the owner's committed
final state, but the previously hydrated PHP object remained stale.

This phase is authorized ONLY to correct that demonstrated stale-state /
idempotent-confirmation problem and then rerun the required engine proof.

4. IDENTICAL RECEIPT CONVERGENCE
============================================================

For the demonstrated race:

Worker A:
confirm contribution using receipt R
→ commit SUCCESS.

Worker B:
was concurrently attempting the SAME contribution with the SAME authoritative
receipt R
→ waits
→ obtains authority after A commits.

Worker B must re-read authoritative state.

If it establishes that:

- the same contribution is already terminal-successful;
- the same authoritative receipt/funding identity is retained;
- the expected amount/currency/economic identity matches;
- canonical effects already exist exactly once;

then B must converge idempotently on the existing successful result.

It must NOT:

- add another contribution;
- add another funded amount;
- duplicate commission;
- duplicate Vendor payable;
- duplicate ledger effects;
- create a replacement receipt;
- reopen the terminal contribution.
