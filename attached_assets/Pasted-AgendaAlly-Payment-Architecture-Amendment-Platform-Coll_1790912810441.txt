AgendaAlly — Payment Architecture Amendment: Platform Collection by Default + Optional Vendor Direct Gateways

This is a correction/refinement to the payment architecture work already completed or currently being implemented.

DO NOT restart the payment audit.
DO NOT discard valid Phase 0 security fixes.
DO NOT redo completed work unnecessarily.
DO NOT activate any payment provider.

Review the current implementation against this amended business rule and make only the changes necessary to align the Phase 0 / foundational Phase 1 implementation with it.

# CORE BUSINESS DECISION

AgendaAlly should use the following hierarchy:

SUPERADMIN
    ↓
Defines which payment methods are permitted for each country
    ↓
AGENDAALLY PLATFORM COLLECTION — DEFAULT
    ↓
Vendor can use the country's supported platform payment methods
without supplying their own merchant gateway credentials
    ↓
OPTIONAL VENDOR DIRECT COLLECTION
    ↓
Vendor may choose to connect their own eligible merchant gateways
only where the payment method, country, currency and provider
support vendor-direct merchant collection

This replaces any implementation assumption that every Vendor must configure their own payment gateway before customers can use that payment method.

# 1. SUPERADMIN OWNS COUNTRY PAYMENT POLICY

Superadmin remains responsible for determining which payment methods are permitted for each country.

Reuse the existing:

country_payments

architecture.

Conceptually:

Country
    ↓
Superadmin-approved payment methods
    ↓
Payment resolver
    ↓
Platform-collected methods
and/or
Vendor-direct-capable methods

A Vendor must NEVER be able to add a payment method that Superadmin has not permitted for the Vendor's authoritative business country.

Country assignment remains policy eligibility only.

It does NOT mean that a provider is:

- globally active
- configured
- legally approved
- integration-ready
- settlement-ready
- payout-ready
- available for real transactions

Preserve all existing readiness/environment/configuration gates.

# 2. PLATFORM COLLECTION SHOULD BE THE DEFAULT MODEL

For supported online payment methods, the default AgendaAlly model should be:

Customer
    ↓
Supported payment method
    ↓
AgendaAlly platform merchant/provider configuration
    ↓
Verified payment
    ↓
AgendaAlly records Vendor liability
    ↓
Vendor becomes eligible for payout under the future payout architecture

This is the DEFAULT architectural collection model.

However, this task does NOT authorize real platform collection yet.

The existing audit already established that Vendor liability, product liability, settlement, payout, refunds and multi-currency accounting are not complete.

Therefore:

IMPLEMENT THE ARCHITECTURAL DEFAULT AND ELIGIBILITY MODEL,

but DO NOT activate platform payment processing merely because platform collection is now the default design.

External providers must remain disabled/fail-closed until their required later phases are approved and completed.

# 3. VENDORS SHOULD NOT NEED THEIR OWN GATEWAY ACCOUNT BY DEFAULT

A Vendor should be able to participate in an AgendaAlly platform-supported payment method without having their own provider merchant/API credentials.

Example architectural behavior:

Cameroon
    ↓
Superadmin permits MTN MoMo
    ↓
AgendaAlly has a valid platform MTN configuration
    ↓
Vendor uses AgendaAlly Payments
    ↓
Customer pays through AgendaAlly's MTN merchant integration
    ↓
Vendor does NOT enter MTN API credentials

The same principle should apply to any future platform-managed provider such as:

- MTN MoMo
- Orange Money
- Paystack
- Flutterwave
- Stripe
- PayPal
- other legitimate platform-managed providers

where the actual provider architecture, country, merchant agreement and regulations support that model.

Do not assume that every listed provider supports this arrangement.

Unknown capability must remain UNKNOWN / unavailable until verified.

# 4. VENDOR DIRECT COLLECTION BECOMES OPTIONAL

Vendors may optionally choose to receive supported payments through their own merchant gateway configuration.

This should be treated as:

VENDOR DIRECT COLLECTION

rather than the default payment model.

Conceptually:

Vendor chooses:
“Use my own payment gateways”
        ↓
Resolver determines Vendor country
        ↓
Country policy determines permitted methods
        ↓
Resolver determines which methods support Vendor-direct collection
        ↓
Vendor configures only those eligible methods
        ↓
Valid merchant configuration is required
        ↓
Customer payment goes through that Vendor's merchant account

Do not show Vendor credential forms for methods that are platform-only.

Do not let Vendors enter arbitrary credentials merely because a Payment catalog record exists.

# 5. CHANGE THE MEANING/PRESENTATION OF collect_via_platform

Preserve the existing:

collect_via_platform

field/API semantics where necessary for compatibility.

Do NOT unnecessarily remove or rename the database field if doing so would affect Laravel, Web, Admin/Vendor or Flutter compatibility.

But change the PRODUCT MODEL so that:

collect_via_platform = true

is the normal/default collection architecture.

The Vendor-facing UI should no longer primarily present:

“Collect via platform”

as an optional feature the Vendor must discover and enable.

Instead, redesign the setting conceptually as:

PAYMENT COLLECTION

How would you like to receive customer payments?

OPTION 1 — DEFAULT / RECOMMENDED

AgendaAlly Payments

“Use payment methods supported by AgendaAlly for your business country. AgendaAlly processes eligible online payments and your earnings are handled through the platform settlement/payout system.”

OPTION 2 — OPTIONAL

My own payment gateways

“Connect eligible merchant payment accounts and receive supported payments directly through your own provider accounts.”

Wording can be refined to fit the existing AgendaAlly UI.

Do not imply that platform payouts are currently operational if the payout architecture is not complete.

In development, clearly represent unavailable/incomplete states.

# 6. DEFAULT FOR NEW VENDORS / SHOPS

For newly created development Vendors/shops, the intended collection preference should be:

collect_via_platform = true

unless there is a strong existing compatibility reason preventing this.

Before changing an existing database default/migration, inspect the current creation path and determine the safest additive approach.

DO NOT rewrite historical shops blindly.

DO NOT reinterpret historical payment transactions.

If changing the schema default would create compatibility problems, implement the default in the appropriate shop creation/service layer and document the reason.

Existing Vendors should not be destructively migrated without an explicit migration policy.

Report exactly how the default is established.

# 7. PERSONAL MOBILE MONEY ACCOUNT IS NOT A MERCHANT GATEWAY

This distinction is critical for African markets.

Many small businesses may have:

- personal MTN MoMo accounts
- personal Orange Money accounts
- ordinary mobile-money phone numbers

without having:

- merchant API credentials
- collection API accounts
- provider merchant contracts

Do NOT treat a personal mobile-money number as equivalent to a payment gateway merchant configuration.

Separate:

PAYMENT COLLECTION CREDENTIALS

from:

PAYOUT DESTINATION

Conceptually:

Collection credentials
→ used to charge/collect customer payments.

Payout destination
→ where AgendaAlly may eventually remit Vendor earnings.

A Vendor's personal MTN/Orange number might eventually be eligible as a payout destination IF the provider, country, KYC requirements and AgendaAlly payout architecture support it.

That is NOT authorization to implement it now.

Do not ask Vendors for personal mobile-money information as merchant API credentials.

# 8. DO NOT IMPLEMENT PAYOUT DESTINATIONS YET

Do not add:

- personal MTN payout
- Orange Money payout
- bank payout
- Stripe payout
- Paystack transfer
- Flutterwave transfer
- automatic settlement

during this amendment.

The future payout architecture must separately determine:

Vendor
+
Country
+
Currency
+
Available liability
+
Payout method
+
Verified destination
+
KYC/provider requirements
+
Reserve
+
Transfer
+
Completion/reconciliation

That belongs to a later approved phase.

# 9. COUNTRY POLICY AND COLLECTION MODE ARE DIFFERENT

Maintain these as separate concepts.

Example:

Cameroon

Superadmin country policy:
- Cash
- MTN MoMo
- Orange Money
- etc.

This does NOT mean every Cameroon Vendor must configure MTN and Orange.

Instead, the resolver should determine:

MTN
Country permitted? YES
Platform supported/configured? maybe
Vendor-direct supported? maybe
Vendor configured direct merchant? maybe
Currency supported? maybe
Provider globally enabled? maybe
Integration ready? maybe

The resulting method can then be classified correctly.

The foundational resolver should be capable of distinguishing at least:

PLATFORM MANAGED

VENDOR DIRECT CAPABLE

BOTH

OFFLINE

INTERNAL / WALLET

and:

AVAILABLE

CONFIGURATION REQUIRED

DISABLED

Do not infer these classifications solely from provider names.

Use actual implementation/configuration capability.

# 11. VENDOR PAYMENT UI

Adjust the Vendor payment-management experience to reflect the new architecture.

The Vendor should first understand their collection model.

When using:

AGENDAALLY PAYMENTS

show the country-permitted platform methods relevant to the Vendor.

Do not request Vendor merchant credentials for those platform-managed methods.

Represent status accurately, for example:

Platform managed
Available through AgendaAlly
Not yet available
Unsupported for your country
Unsupported currency

depending on actual resolver state.

When using:

MY OWN PAYMENT GATEWAYS

show ONLY methods that:

- are permitted by Superadmin for the Vendor's country
- support Vendor-direct collection
- are globally/integration enabled as required
- support the relevant currency
- genuinely consume Vendor-owned merchant credentials

Only then show the appropriate credential/configuration form.

# 12. PLATFORM-ONLY PROVIDERS

Providers configured centrally by AgendaAlly must not expose merchant credentials to Vendors.

For example, if Stripe is configured as a platform rail:

Vendor sees:

Stripe
Managed by AgendaAlly

not:

Enter Stripe secret key

unless AgendaAlly later explicitly supports a legitimate Vendor-direct Stripe model.

Apply the same rule to other platform-managed providers.

# 14. CASH

Cash remains conceptually separate.

Cash / Pay at business:

Customer
    ↓
Vendor receives payment offline

AgendaAlly does not automatically hold those funds.

Do not create Vendor platform liability merely because an order/booking is marked cash-paid unless the accounting rules explicitly require a platform commission receivable.

Do not change accounting behavior in this amendment.

# 15. WALLET

Wallet remains an internal balance mechanism.

Do not treat:

Wallet

as equivalent to:

AgendaAlly platform gateway collection

or:

Vendor merchant gateway.

The audit already identified accounting issues around split-wallet transactions.

Do not expand wallet behavior in this task.

# 16. CUSTOMER CHECKOUT RESOLVER

Customer checkout should continue using the authoritative server resolver.

Conceptually:

Owned booking/cart/order
        ↓
Authoritative Vendor/shop
        ↓
Vendor business country
        ↓
Superadmin country payment policy
        ↓
Transaction currency/type
        ↓
Vendor collection preference
        ↓
Platform or Vendor-direct capability
        ↓
Exact valid configuration
        ↓
Provider readiness/environment
        ↓
Eligible payment methods

If Vendor uses default AgendaAlly Payments:

use eligible PLATFORM configuration.

If Vendor uses My own payment gateways:

use eligible VENDOR configuration.

Never fall back from missing Vendor credentials to platform credentials silently unless the Vendor is actually in platform collection mode.

Never fall back from unavailable platform configuration to Vendor credentials unless Vendor direct collection is explicitly selected/configured.

# 17. PRODUCT AND BOOKING CONSISTENCY

Apply the same collection-model concept to:

- service bookings
- product checkout

Do not solve the later accounting differences yet.

But the eligibility resolver should not treat platform-vs-direct collection differently merely because one transaction is a booking and the other is a product.

Where current backend differences prevent full consistency, fail closed and document the dependency.
