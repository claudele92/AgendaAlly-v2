AgendaAlly — Phase 3B-2
MTN Durable Payment-Attempt Schema + Bounded Identity Containment

The Phase 3B-1 stop report is accepted.

I explicitly approve implementation of the MINIMUM MTN payment-attempt identity
schema proposed in:

docs/development/payment-phase3b-mtn-identity-containment.md

and the bounded application changes required to use it.

This approval is specifically for correcting the source-confirmed MTN
pre-dispatch identity / unknown-outcome recovery defect.

It does NOT approve MTN activation or resume the broader Cameroon/XAF
certification.

============================================================
1. ACCEPTED PROBLEM
============================================================

Phase 3B and Phase 3B-1 established:

- MTN RequestToPay is asynchronous.
- Status reconciliation depends on the original request reference.
- AgendaAlly currently can send RequestToPay before that reference is durably
  recoverable.
- `payment_process.id` lacks a primary-key/unique constraint.
- The current schema does not establish a unique immutable relationship between
  one MTN provider attempt and its canonical funding event.
- There is no sufficient dedicated dispatch/recovery lifecycle.
- Existing canonical contribution idempotency protects downstream accounting
  but does NOT by itself establish pre-dispatch provider-attempt identity.
- No duplicate Customer debit has been demonstrated.

The defect remains UNCONTAINED.

============================================================
2. AUTHORIZED SCHEMA
============================================================

Implement the minimum schema proposed in the accepted Phase 3B-1 report.

The resulting model must establish:

ONE CANONICAL PAYMENT ATTEMPT
→ ONE MTN PROVIDER ATTEMPT
→ ONE IMMUTABLE MTN REQUEST REFERENCE
→ ONE RECOVERABLE DISPATCH/RECONCILIATION LIFECYCLE
→ AT MOST ONE CANONICAL FUNDING EFFECT.

Do not treat merely adding uniqueness to `payment_process.id` as sufficient
unless the accepted proposal demonstrates that this also establishes all of
the required provider-attempt invariants.

The financial/economic identity remains the accepted Phase 2 model.

Provider-attempt identity is a separate protocol layer.

============================================================
3. MATERIAL-DEVIATION GATE
============================================================

Before migration, compare the implementation you are about to create against
the exact schema proposal in the Phase 3B-1 report.

If implementation requires a MATERIAL deviation involving:

- another table not approved by that proposal;
- materially different provider-attempt identity;
- different canonical-payment binding;
- different merchant/configuration identity;
- different contribution identity;

- changes to commission semantics;
- changes to custody;
- changes to Vendor payable semantics;

STOP BEFORE MIGRATION.

Report the deviation and minimum revised proposal.

Do not silently redesign the approved accounting architecture.

============================================================
4. MIGRATION SAFETY
============================================================

The migration must be additive/conservative.

Do NOT infer missing historical MTN identities.

Do NOT fabricate provider references.

Do NOT pair historical Transactions, PaymentProcesses or contributions using
heuristics.

Do NOT reinterpret historical payments.

Existing ambiguous/legacy records must remain legacy/fail-closed as specified
by the accepted proposal.

All 12 legacy Product Orders must remain:

fulfillment_financial_state = unverified.

============================================================
5. PAYMENT_PROCESS.ID
============================================================

Address the documented lack of uniqueness for `payment_process.id` exactly as
required by the accepted schema proposal.

Before adding any uniqueness constraint to existing data:

inspect for collisions.

If existing rows violate the proposed constraint:

STOP.

Do NOT delete, merge, renumber or rewrite them automatically.

Report:

LEGACY PAYMENT_PROCESS ID COLLISION REQUIRES DECISION.

If no collisions exist, proceed only according to the approved migration.

============================================================
6. PROVIDER-ATTEMPT IDENTITY
============================================================

The durable MTN provider-attempt record/binding must establish the approved
immutable relationship among the required identities, including as applicable:

- canonical checkout/payment attempt;
- payable / Order / Booking;
- Transaction;
- provider = MTN;
- Shop;
- collection model;
- merchant owner;
- immutable merchant/configuration revision;
- MTN request reference;
- canonical contribution/funding identity.

Use the exact accepted proposal rather than inventing additional identity.

============================================================
7. REQUEST REFERENCE
============================================================

The MTN request reference must be:

- server generated;
- durable;
- unique at the correct provider boundary;
- immutable after reservation;
- persisted before RequestToPay;
- committed before RequestToPay;
- reused for reconciliation;
- reused by retry/recovery of the same attempt.

No Customer-controlled value may replace it.

============================================================
8. DISPATCH LIFECYCLE
============================================================

Implement the minimum approved lifecycle necessary to distinguish states such
as:

IDENTITY RESERVED / PRE-DISPATCH

DISPATCH OUTCOME UNKNOWN

RECONCILABLE / PENDING

TERMINAL SUCCESS

TERMINAL FAILURE

or the exact equivalent states defined by the accepted schema proposal.

Do not use `paid` to mean merely:

reference persisted
or
request dispatched.

Transport lifecycle and financial finality must remain distinct.

============================================================
9. COMMIT BEFORE DISPATCH
============================================================

This is a mandatory invariant:

THE DURABLE MTN ATTEMPT AND REQUEST REFERENCE MUST COMMIT BEFORE THE EXTERNAL
REQUEST CAN BE SENT.

Do not hold an open database transaction across the external MTN network call
as a substitute for durability.

The fake transport tests must be able to observe that the identity is already
committed when dispatch begins.

============================================================
10. UNKNOWN OUTCOME
============================================================

If RequestToPay may have been transmitted but AgendaAlly does not know the
outcome:

retain the original provider attempt;
retain the original request reference;
do not generate another reference;
do not mark paid;
do not confirm funding;
do not recognize commission;
do not create Vendor payable;
do not assume failure merely to allow another attempt.

Recover by reconciling the original reference.

============================================================
11. DEFINITELY UNSENT
============================================================

If an attempt has a persisted identity but dispatch can be proven never to have
occurred, follow the exact approved lifecycle.

Do not confuse:

DEFINITELY UNSENT

with:

MAY HAVE BEEN SENT.

If transport state is ambiguous, choose UNKNOWN/fail-closed recovery.

============================================================
12. RETRY
============================================================

A retry of the SAME canonical payment attempt must not create a second MTN
provider attempt merely because:

- Customer refreshed;
- frontend retried;
- HTTP timed out;
- worker restarted;
- callback was delayed;
- process crashed;
- response handling failed;
- reconciliation was temporarily unavailable.

Reuse/reconcile the durable provider identity.

A genuinely new provider attempt is allowed only under the accepted terminal
retry rules.

============================================================
13. RECONCILIATION
============================================================

Reconciliation must start from the persisted server-owned provider attempt.

It must use the original MTN request reference.

It must retain the accepted verification requirements for:

- provider;
- amount;
- currency;
- merchant context where provable;
- Shop/context;
- canonical payment identity.

Do not allow a Customer-supplied provider reference to become authoritative.

============================================================
14. FINANCIAL AUTHORITY
============================================================

Do not weaken the accepted authority model.

None of these proves payment:

- provider attempt exists;
- reference exists;
- dispatch occurred;
- initiation HTTP success;
- Customer redirect;
- callback hint;
- frontend status;
- Order/Booking lifecycle status.

Only authoritative provider verification/reconciliation may establish funded
MTN accounting.

============================================================
15. CANONICAL ACCOUNTING
============================================================

Do not redesign Phase 2 accounting.

Before authoritative success:

confirmed contribution = 0
commission effect = 0
Vendor payable effect = 0.

After authoritative success:

the existing canonical accounting path may execute exactly once.

The provider-attempt layer must feed the existing accounting identity rather
than replace it.
