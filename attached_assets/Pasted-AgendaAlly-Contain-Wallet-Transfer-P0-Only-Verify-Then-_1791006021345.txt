AgendaAlly — Contain Wallet Transfer P0 Only, Verify, Then Stop

I approve remediation ONLY for the newly confirmed Wallet transfer P0 documented
in:

docs/development/payment-system-full-audit.md

Do not resume the broader payment architecture audit yet.

The defect to contain is:

A successful Wallet transfer debits the sender and credits the recipient, but
the sender-side withdrawal remains `processed`. The sender can subsequently
cancel that debit through their own Wallet history, restoring their balance
without reversing the recipient credit and therefore creating unbacked Wallet
value.

============================================================
1. OBJECTIVE
============================================================

Implement the minimum correct containment for this Wallet transfer lifecycle.

The required invariant is:

A COMPLETED TRANSFER MUST CONSERVE VALUE.

Once the recipient has been successfully credited, the sender must not be able
to independently cancel/reject/reverse the sender debit and restore their
balance while leaving the recipient credit intact.

Do not solve this merely with an ownership check.

The current exploit uses the sender's OWN Wallet history, so ownership alone is
not the missing accounting boundary.

============================================================
2. INVESTIGATE THE NATIVE MODEL FIRST
============================================================

Before changing code, trace the existing Wallet lifecycle and determine the
smallest native-compatible correction.

Inspect at minimum:

POST /api/v1/dashboard/user/wallet/send

GET /api/v1/dashboard/user/wallet/histories

POST /api/v1/dashboard/user/wallet/history/{uuid}/status/change

and the relevant:

- WalletController;
- WalletHistoryService;
- WalletHistory model;
- Transaction model;
- observers/listeners;
- status enums/constants;
- existing Wallet tests.

Establish whether the native model already has an appropriate terminal state or
transfer relationship that should be used.

Do not invent a large new Wallet architecture if a smaller correct lifecycle
fix exists.

============================================================
3. REQUIRED ACCOUNTING BEHAVIOR
============================================================

For a successful internal transfer of x:

Before:
Sender = A
Recipient = B

After completed transfer:
Sender = A - x
Recipient = B + x

Combined balance must remain:

A + B

A later sender action must NEVER result in:

Sender = A
Recipient = B + x

unless a legitimate atomic reversal also removes x from the recipient according
to an explicitly supported reversal workflow.

For this containment, prefer making a successfully completed transfer FINAL /
NON-CANCELLABLE from the ordinary customer history-status route unless the
existing architecture clearly defines a safe paired reversal mechanism.

Do not create a new customer-accessible reversal capability merely to preserve
the existing cancellation action.

============================================================
4. TRANSFER PAIR INTEGRITY
============================================================

Determine whether the sender debit and recipient credit currently have a
reliable shared transfer identity.

If one already exists, use it appropriately.

If none exists, determine whether introducing one is necessary for the minimum
safe containment.

Do not add schema merely for architectural elegance if preventing cancellation
of completed transfers safely solves the P0.

However, do not rely on fragile inference such as:

- amount alone;
- timestamp alone;
- sender/recipient alone;
- neighboring row IDs.

Document the decision.

============================================================
5. STATUS LIFECYCLE
============================================================

Establish the correct state transitions for:

- pending transfer;
- failed transfer;
- successfully completed transfer;
- cancellable withdrawal;
- rejected withdrawal;
- canceled withdrawal.

A transfer that has already credited its recipient must not remain in a state
that the generic customer cancellation path interprets as cancellable.

Preserve legitimate cancellation behavior for operations that truly remain
cancellable.

Do not globally disable Wallet cancellation unless that is actually required
by the native model.

============================================================
6. ATOMICITY
============================================================

Preserve the existing atomic initial transfer behavior.

A successful send must still behave as one financial operation:

sender debit + recipient credit

or neither.

Verify that failures during recipient credit cannot leave only the sender debit
committed.

Also verify that the containment does not introduce a new partial-transfer
state.
