# ADDITIONAL BOUNDED WORKSTREAM — Fix Vendor Payment Collection Settings UX and Persistence

While completing the Maps/location task, also audit and correct the existing Vendor “Payment collection” settings experience.

This is NOT a new payment architecture phase.

The underlying payment resolver, country policy, frozen intents, provider hardening and AgendaAlly Payments architecture must remain authoritative.

The current Vendor screen is not acceptable as a production-facing settings experience.

It currently shows:

Payment collection

“Choose how customer payments are collected for this transaction type. No merchant API credentials are required to use AgendaAlly Payments. This setting does not confirm that a payment was received or that payouts are available. Payout methods are separate and are not configured here.”

Collection choices:

- AgendaAlly Payments · Recommended
- Use my own payment gateway

But it also exposes implementation/debugging information such as:

transaction.currency: XAF
payment.policy.status

currency.supported
configured
collector_not_configured
collector_disabled

environment_disabled
etc.

It also appears to require choosing either Services OR Products, with no obvious “Both” option, even though an AgendaAlly Vendor may sell products and provide services.

There is also no clear Save/Submit/Apply action.

Audit the complete implementation and correct it properly.

Credit use is important. Do not reopen the broad payment architecture audit.

## 1. Trace the current implementation before changing UI

Trace:

Vendor Payment collection UI
→ transaction-type state
→ collection-mode state
→ resolver/policy request
→ save/update endpoint
→ Laravel validation
→ service/model
→ persisted shop/payment configuration
→ checkout consumption.

Determine exactly:

- what Services means;
- what Products means;
- whether these are stored independently;
- whether collection mode is currently one shop-wide setting or transaction-type-specific;
- whether selecting a radio currently saves immediately;
- whether there is an existing save endpoint;
- whether the UI is showing unsaved state as if it were persisted;
- whether changing transaction type changes the actual persisted policy;
- how existing `collect_via_platform` compatibility is represented;
- how the newer AgendaAlly Payments/default-platform model interacts with it.

Do not guess.

## 2. Support businesses that offer BOTH Services and Products

A Vendor may:

- provide Services only;
- sell Products only;
- do both.

The settings experience must support this naturally.

Preferred Vendor-facing choices:

Transaction type

[ Services ]
[ Products ]
[ Services & Products ]

or an equivalent polished control consistent with the current Admin/Vendor UI.

“Services & Products” should mean:

Apply this collection preference to both service transactions and product transactions.

However:

DO NOT introduce a fake backend `both` transaction type if the financial/payment architecture requires separate service and product policy records.

If Services and Products are stored separately, the UI may present “Services & Products” while the server safely validates and updates both underlying configurations.

The operation must be atomic where practical:

either both intended settings are updated,
or neither is.

Do not leave one updated and the other stale after a partial failure.

## 3. Determine whether separate Service/Product collection settings are actually necessary

Audit the underlying architecture.

If the collection mode is genuinely shop-wide and Services/Products cannot currently have different modes, do not preserve a meaningless transaction selector merely because it already exists.

In that case, simplify the Vendor UI appropriately.

If the architecture intentionally supports:

Services → AgendaAlly Payments
Products → Vendor gateway

or the inverse, preserve that capability.

The UI should then clearly show the saved setting for each transaction type.

Do not change the financial architecture merely to make the UI easier.

## 4. Add an explicit Save action

Payment collection configuration must have a clear persistence action.

Use a production-quality action such as:

Save payment settings

or:

Save changes

The exact wording can follow the existing Vendor design system.

The Vendor should be able to understand:

- current saved configuration;
- pending changes;
- saving state;
- successful save;
- validation failure;
- server failure.

Do not rely on an ambiguous radio click if the current UI gives no indication that it immediately changed a consequential business setting.

If the existing endpoint is toggle-based, audit it carefully.

Prefer an idempotent desired-state contract such as:

set collection mode = platform

rather than:

toggle collection mode

if the current architecture allows this bounded correction.

Do not create a second competing settings model.

## 5. Default behavior

Preserve the approved architecture:

AgendaAlly Payments is the recommended/default collection model for new Vendors.

The Vendor may opt into:

Use my own payment gateway

only when the business context and payment resolver determine that Vendor-direct collection is supported.

Do not automatically enable a provider.

Do not fabricate merchant configuration.

Do not treat a personal phone/mobile-money account as a merchant gateway unless the actual provider integration supports that account type.

## 6. Vendor-facing design

Redesign this particular settings block to match the current AgendaAlly Admin/Vendor design system.

It should feel like a business setting, not a developer diagnostics screen.

Suggested information hierarchy:

Refine the wording based on what the implementation actually supports.

Do NOT make unsupported claims about settlement or payout availability.

## 8. Replace diagnostics with actionable Vendor information

The Vendor should primarily see methods they can actually use.

For AgendaAlly Payments, a concise section may say, for example:

Available through AgendaAlly

Cash
Other eligible methods configured by AgendaAlly

Only display methods actually returned as eligible by the authoritative resolver.

For Vendor-direct mode:

Show only payment methods that:

- are Vendor-configurable;
- are permitted for the Vendor's authoritative business country;
- support the transaction type;
- support the authoritative transaction currency;
- are integration-ready;
- are permitted by environment policy.

If none are available, say something understandable such as:

“No supported Vendor-managed payment gateway is currently available for this business configuration.”

Do not show 15–20 unusable gateways with raw failure flags.

## 9. Country and currency presentation

Do not show:

Do not allow the Vendor to manipulate country/currency from this payment block merely to unlock payment methods.

Those remain authoritative business/location/currency settings.

## 10. Own-gateway configuration

If the Vendor selects:

Use my own payment gateway

then show/configure only genuinely supported Vendor-owned gateways.

From the previous payment audit, do not resurrect generic credential forms for providers whose global platform credentials are not actually consumed from `shop_payments`.

In particular, do not make Stripe/PayPal/etc appear Vendor-configurable merely because legacy generic client/secret fields exist.

Use the authoritative capability/resolver work already implemented.

Vendor-owned credentials must remain:

- shop scoped;
- encrypted where required;
- redacted;
- ownership protected;
- country/currency/type constrained.

## 11. AgendaAlly Payments does NOT require Vendor merchant credentials

When AgendaAlly Payments is selected:

Do not ask the Vendor for AgendaAlly's:

- Stripe keys;
- PayPal credentials;
- MTN platform credentials;
- Orange platform credentials;
- Flutterwave keys;
- Paystack keys;
- or any other platform merchant credential.

Those remain Superadmin/platform configuration.

Vendor payout configuration is also separate.

## 12. Keep payout settings separate

Do not add payout destination configuration to this Payment collection card.

The conceptual separation remains:

Customer payment collection
≠
Vendor payout destination.

A Vendor choosing AgendaAlly Payments means the platform may collect eligible customer payments according to payment policy.

It does NOT by itself mean:

- funds are already settled;
- earnings are immediately withdrawable;
- payout setup is complete;
- payout accounting is implemented.

Use accurate wording.

## 13. Preserve existing businesses and frozen transactions

Do not reinterpret historical transactions.

Do not rewrite frozen payment intents.

Do not automatically migrate existing Vendors from one collection mode to another merely because AgendaAlly Payments is now the default for NEW Vendors.

Existing saved collection choices must remain intact unless there is a proven invalid legacy state requiring explicit migration.

If migration is required, report it before destructive changes.
