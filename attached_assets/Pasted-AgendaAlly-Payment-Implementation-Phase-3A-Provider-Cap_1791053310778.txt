AgendaAlly — Payment Implementation Phase 3A
Provider Capability, Merchant Configuration & Runtime Readiness

Phase 2B and Phase 2C are accepted within their documented scopes.

The canonical payment/accounting foundation is now the authoritative baseline.

Accepted baseline includes:

- Canonical Shop economic allocations.
- Immutable funding/collection contributions.
- Commission calculated once per Shop economic allocation.
- Platform-held funds satisfy commission first.
- Remaining eligible platform-held value becomes Vendor payable.
- Vendor-direct and Vendor-received Cash principal do not create platform
  principal payout liability.
- Verified Wallet debit is platform-controlled funding.
- Unsatisfied commission is represented separately as Vendor commission
  receivable.
- Original contribution/custody evidence is immutable.
- Replacement Transactions and duplicate callbacks cannot duplicate canonical
  commission/allocation/payable.
- Supported Product and Booking Cash, Wallet and verified electronic paths
  reach canonical accounting.
- Unsupported/unproven monetary contracts fail closed.
- Same-currency XAF accounting is supported within the documented Phase 2C
  limits.
- All 12 legacy Product Orders remain
  `fulfillment_financial_state = unverified`.
- Production-engine concurrency remains NOT CERTIFIED.
- No production deployment/payment activation has been approved.

Phase 3A is authorized to correct and verify the PROVIDER CONFIGURATION
ARCHITECTURE.

This is NOT authorization to process real payments.

============================================================
1. PRIMARY OBJECTIVE
============================================================

Implement and verify a clean separation between:

A. PROVIDER CAPABILITY

What the AgendaAlly integration is designed to support:

- country;
- currency;
- payment method;
- platform-managed collection;
- Vendor-direct collection;
- verification;
- callbacks/webhooks;
- refunds;
- payout/remittance capabilities where applicable.

B. MERCHANT CONFIGURATION

Whether the appropriate merchant owner has supplied the configuration required
for that collection model.

Merchant owner may be:

- AgendaAlly/platform;
- Vendor/Shop.

C. RUNTIME READINESS

Whether the configured integration is actually operationally ready:

- required credentials present;
- verifier implemented;
- callback/webhook implementation present;
- required callback URL/configuration present;
- environment requirements satisfied;
- provider-specific requirements satisfied.

D. CHECKOUT AVAILABILITY

Whether a Customer may actually use that provider for THIS payment given:

- capability;
- merchant configuration;
- runtime readiness;
- country;
- currency;
- collection model;
- Shop;
- canonical quote compatibility;
- current environment/activation policy.

These concepts MUST NOT be collapsed into one boolean.

In particular:

NOT CONFIGURED

must not mean:

UNSUPPORTED.

And:

SUPPORTED

must not mean:

READY FOR CUSTOMER PAYMENT.

============================================================
5. CAPABILITY MUST BE STATIC / AUTHORITATIVE
============================================================

Provider capability must answer:

"Can this AgendaAlly integration support this combination in principle?"

It must NOT depend on whether credentials happen to exist today.

Capability should consider:

- provider;
- country;
- currency;
- payment method;
- collection mode;
- implementation capability.

Do not mark a provider unsupported merely because:

- credentials are absent;
- environment variables are absent;
- merchant configuration has not been entered;
- provider is disabled for checkout;
- callback URL is not configured.

Those are readiness/configuration concerns.

============================================================
6. CONFIGURATION MUST BE OWNER-AWARE
============================================================

Merchant configuration must be evaluated against the COLLECTION OWNER.

For platform-managed collection:

configuration belongs to AgendaAlly/platform.

For Vendor-direct collection:

configuration belongs to the Vendor/Shop merchant relationship.

Do not accidentally use platform credentials to declare a Vendor-direct
merchant configured.

Do not accidentally use Vendor credentials to declare platform-managed
collection configured.

Merchant ownership must be persisted/source-proven.
