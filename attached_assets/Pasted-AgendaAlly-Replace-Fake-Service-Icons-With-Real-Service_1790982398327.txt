Add this scope to the approved Customer storefront/discovery design pass.

The current Shop profile is displaying generic/mock icon-style graphics for Services, for example Bridal Makeup, Beard Trim, Massage Therapy and Manicure.

This does NOT match the approved Shop-profile design direction.

Services should use real, relevant photographic images where a Service image exists.

IMPORTANT:
Credit use is important.

Do not perform another broad Shop-profile audit.
Do not redesign the Shop page again.
The existing Shop-profile layout is approved.

This task is specifically to:

1. Audit the existing Service image/media architecture.
2. Correct any incomplete Service-image storage/upload/read/display flow.
3. Ensure Vendors can manage Service images through the existing Service management flow where appropriate.
4. Seed appropriate real photographic images for the EXISTING development/demo Services.
5. Replace the current fake/generic Service icons on seeded demo Services with those real images.
6. Preserve safe fallback behavior for Services that genuinely have no image.

==================================================
1. AUDIT THE EXISTING SERVICE IMAGE MODEL FIRST
==================================================

Before adding another image field or media system, trace the existing native Service media flow end-to-end.

Audit:

Service database/model
    ↓
Service create/update request
    ↓
Vendor Service management UI
    ↓
upload/storage handling
    ↓
local/S3 storage
    ↓
API serialization
    ↓
Customer storefront
    ↓
Service card/image

Determine:

- whether Service already has an image/media relationship;
- database fields/relationships involved;
- whether one image or multiple images are supported;
- upload endpoint;
- file validation;
- storage disk/path;
- local development behavior;
- S3/cloud behavior;
- URL generation;
- deletion/replacement behavior;
- ownership authorization;
- Vendor UI support;
- Admin support if applicable;
- Customer API representation;
- current fallback/icon behavior.

The previous Shop-profile work already reported:

“Service images are optional; canonical native local/S3 media URLs are checked against ownership boundaries.”

START from that existing implementation.

Do NOT create a competing Service image architecture if that implementation already provides the required capability.

==================================================
2. VENDOR SERVICE IMAGE MANAGEMENT
==================================================

Verify that an authorized Vendor can manage images for Services belonging to that Vendor/shop.

The normal Service create/edit experience should support an appropriate Service image where the native architecture permits it.

Conceptually:

Service name
Category
Description
Duration
Price
Location/mode
Service image
[Upload / Replace image]
[Save]

Do not force Vendors to provide an image.

Service images remain OPTIONAL.

Enforce ownership server-side.

Vendor A must never be able to replace/delete/read private management metadata for Vendor B's Service image by forging:

- Service ID;
- shop ID;
- media ID;
- upload association;
- request payload.

Preserve existing Admin/Superadmin authority where intentionally supported.

==================================================
3. IMAGE VALIDATION
==================================================

Use the application's existing media validation conventions where possible.

Validate appropriate:

- MIME/file type;
- maximum size;
- supported image formats;
- image ownership;
- storage destination.

Do not accept arbitrary files merely because the extension looks like an image.

Do not weaken existing media security.

==================================================
4. STORAGE
==================================================

Use the existing native media/storage abstraction.

Development may use the existing local storage implementation.

Production/cloud must continue supporting the application's intended S3/object-storage path if already implemented.

Do NOT:

- hard-code Replit filesystem paths into database records;
- store base64 images in Service rows;
- create a second Service-media subsystem;
- make Customer pages depend on temporary development URLs.

Persist the canonical media reference expected by AgendaAlly and resolve URLs through the existing media/storage layer.

==================================================
5. REPLACEMENT AND DELETION
==================================================

Audit Service image replacement/removal.

When replacing an image:

- update the authoritative Service/media association;
- avoid leaving unnecessary orphaned files where the native cleanup architecture supports safe deletion;
- never delete another shop's media;
- do not delete shared media if the architecture allows media reuse.

When removing an image:

Service should return to the approved fallback state.

Do not make image removal delete the Service.

10. IMAGE SOURCING / SEED SAFETY
==================================================

Prefer assets already owned/provided in the project or properly usable demo assets.

Do not introduce unstable hotlinks to random third-party images.

Seed through AgendaAlly's normal media/storage representation rather than storing arbitrary external URLs if that is not the application's native model.

The seed MUST be guarded and idempotent.

Running it twice must:

- create zero duplicate Services;
- create zero duplicate media associations;
- avoid repeatedly replacing already-correct Service media;
- avoid changing legitimate Vendor-uploaded images;
- avoid touching unrelated media.

Restrict demo media updates to clearly owned development/seed records.
