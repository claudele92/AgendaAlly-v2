APPROVED — resume the Payment System Completion Program across the defined
schema/identity boundary.

The bounded proposal in
`docs/development/payment-system-completion.md`
is approved for implementation.

This approval covers ONLY the minimum durable identity infrastructure required
to complete the already-authorized payment work:

1. Immutable global merchant configuration revisions.
2. Generic durable electronic collection attempts.
3. Durable refund operation identity and original-contribution linkage.
4. Durable commission-receivable settlement operation/receipt identity.
5. Durable Vendor-payable reservation and payout/settlement operation identity.

The objective is to unblock the existing completion program, NOT redesign the
accepted payment economics.

============================================================
1. ACCEPTED FINANCIAL MODEL REMAINS AUTHORITATIVE
============================================================

Do not change the accepted Phase 2 accounting model.

Preserve:

- one canonical Shop economic allocation;
- frozen original collection/custody context;
- commission calculated once;
- platform-held funds satisfy commission first;
- remaining eligible platform-held value creates Vendor payable;
- Vendor-direct principal does not create platform principal payable;
- Vendor-received Cash does not create platform principal payable;
- unsatisfied commission becomes Vendor commission receivable;
- replacement Transactions cannot duplicate canonical economics;
- refunds follow original custody;
- settlement/payout effects are append-only/once-only;
- current Wallet conservation/finality;
- current payout atomicity protections;
- current fulfillment finality;
- existing payment authorization containments.

Do not reinterpret historical financial records.

============================================================
2. GLOBAL MERCHANT CONFIGURATION REVISIONS
============================================================

Implement immutable revisions for the existing global platform provider
configurations used by:

- Flutterwave
- Paystack
- Stripe
- PayPal

The revision must preserve the provider/merchant configuration identity needed
to establish which configuration was used for a payment.

A payment attempt/contribution must bind to the exact original revision.

Later Admin credential/configuration rotation must create/use a new revision
rather than rewriting the historical merchant identity used by an earlier
payment.

Do not fabricate revisions for historical payments where original evidence is
insufficient.

Do not silently classify legacy records.

Secrets remain encrypted/redacted.

Do not duplicate secrets into unnecessary financial/accounting records.

============================================================
3. GENERIC DURABLE COLLECTION ATTEMPT
============================================================

Implement a durable generic provider-attempt identity for non-MTN electronic
providers.

It must support the equivalent financial invariant already established for MTN:

canonical funding identity
→ durable provider attempt
→ original configuration revision
→ durable pre-dispatch claim
→ provider dispatch
→ pending/unknown/success/failure
→ authoritative verification/reconciliation
→ canonical funding exactly once.

The attempt must exist before external provider dispatch.

Do not treat a frontend request, eligible payment method or provider initiation
response as paid authority.

============================================================
4. PROVIDER REFERENCE
============================================================

Retain the original provider reference/identity separately from internal
attempt identity.

Once provider dispatch can have occurred, the provider reference/configuration
identity must not be silently replaced in a way that loses recovery of the
original attempt.

UNKNOWN must remain recoverable where the provider contract permits it.

UNKNOWN is not paid.

UNKNOWN must not cause blind resubmission.

Provider-specific retry behavior must still follow the authoritative provider
contract.

============================================================
5. MTN MUST REMAIN UNCHANGED
============================================================

Do not migrate MTN onto the generic attempt model merely for uniformity.

The accepted typed MTN durable identity/recovery implementation remains
authoritative unless an actual MTN contract requirement later proves a change
necessary.

The new generic infrastructure may share abstractions where safe, but must not
weaken or rewrite the accepted MTN guarantees.

MTN remains disabled.

============================================================
6. REFUND OPERATION IDENTITY
============================================================

Implement durable refund-operation identity.

Every electronic refund must retain:

- original canonical allocation;
- original contribution(s);
- original collector/custody;
- original provider;
- original merchant/configuration revision;
- original provider payment identity;
- requested refund amount;
- provider refund reference when available;
- operation state;
- canonical refund effect identity.

Retries, callbacks, polling and Admin retries must converge on the same
operation rather than creating another economic refund.

Partial refunds must retain cumulative/refundable limits.

Do not use current provider settings to reinterpret an old payment.

============================================================
7. REFUND RESERVATION
============================================================

Prevent concurrent or repeated refund requests from authorizing more than the
remaining refundable amount.

The durable operation/reservation must fail closed when original custody or
provider evidence is insufficient.

A provider timeout/unknown result must not release authority in a way that
allows another potentially duplicate provider refund.

Do not mark a refund complete before authoritative provider evidence where an
external provider refund is required.

============================================================
8. COMMISSION RECEIVABLE SETTLEMENT
============================================================

Implement the minimum durable operation/receipt identity required to settle a
Vendor commission receivable legitimately.

The workflow must distinguish:

ACCOUNTING RECEIVABLE

from:

ACTUAL RECEIPT/COLLECTION OF THAT RECEIVABLE.

A receivable may become settled only from legitimate retained evidence of
receipt/collection.

Do not invent an automatic Vendor debit.

Do not debit an Admin Wallet merely because an Admin approves settlement.

Prevent duplicate settlement of the same receivable amount.

============================================================
9. VENDOR PAYABLE / PAYOUT OPERATION
============================================================

Implement durable reservation/operation identity for Vendor payouts.

The workflow must distinguish:

VENDOR PAYABLE
→ RESERVED FOR PAYOUT
→ EXTERNAL PAYOUT ATTEMPT
→ UNKNOWN/PENDING
→ AUTHORITATIVE SUCCESS/FAILURE
→ CANONICAL SETTLEMENT EFFECT.

A Vendor payable must not be paid twice through concurrent requests, stale
models, Admin retries or provider retry.

Do not mark external payout success merely because internal bookkeeping
succeeded.

============================================================
10. PAYOUT FUNDING
============================================================

Do not restore the previously incorrect model where an approving Admin's Wallet
funds Vendor payout principal.

Vendor payout principal must correspond to legitimate platform Vendor liability
and legitimate platform-controlled funds.

If the repository does not yet have an approved external payout rail or
authoritative external platform-funding source:

complete the durable internal workflow but retain:

EXTERNAL PAYOUT NOT READY.

Do not invent a rail.

============================================================
11. SCHEMA PRINCIPLES
============================================================

Prefer additive schema.

New identity/operation records must have:

- server-owned primary identity;
- appropriate unique constraints;
- immutable economic/merchant bindings;
- explicit lifecycle state;
- timestamps/auditability;
- safe foreign-key retention behavior;
- indexes required for lookup/reconciliation;
- database-level uniqueness for once-only financial effects where appropriate.

Do not rely solely on application-level "check then insert" for financial
uniqueness.

============================================================
12. LEGACY DATA
============================================================

Do not backfill historical financial meaning that cannot be proven.

Existing legacy provider/configuration/payment rows may remain:

UNCLASSIFIED
UNVERIFIED
or
LEGACY

as appropriate.

All existing 12 legacy Product Orders remain `unverified`.

Do not delete them.

Do not rewrite historical financial records to make the new schema appear
complete.

============================================================
13. MIGRATION SAFETY
============================================================

Before applying migrations:

- capture the current protected-state baseline;
- inspect existing rows for uniqueness/foreign-key conflicts;
- prove migration ordering;
- prove rollback behavior where reasonably possible;
- use nullable/additive linkage for unclassified historical records where
  appropriate.

Apply approved migrations only to the owned development database after
disposable migration verification passes.

No production database access.

============================================================
14. CONCURRENCY
============================================================

Test the new identities with controlled two-connection SQLite cases where
applicable.

Cover at minimum:

- duplicate attempt creation;
- concurrent dispatch claim;
- duplicate provider finalization;
- concurrent refund reservation;
- duplicate refund finalization;
- concurrent receivable settlement;
- concurrent Vendor payable reservation;
- duplicate payout finalization.

The existing disposable MySQL harness should be extended/prepared for these
identities.

If no disposable MySQL instance is available, do not block application
completion solely for that reason.

Retain:

PRODUCTION-ENGINE CONCURRENCY NOT CERTIFIED.
