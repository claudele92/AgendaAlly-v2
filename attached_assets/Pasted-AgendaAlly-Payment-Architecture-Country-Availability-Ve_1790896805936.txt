AgendaAlly — Payment Architecture, Country Availability, Vendor Configuration, Currency Routing & Settlement Audit

The Stage 2 storefront/UI work is complete enough for now.

The next task is a focused PAYMENT ARCHITECTURE AUDIT of the existing AgendaAlly application.

DO NOT redesign payment UI yet.
DO NOT implement broad payment changes yet.
DO NOT activate providers.
DO NOT perform real transactions.
DO NOT request payment credentials.

First determine exactly how the existing Laravel, Admin/Vendor, Customer Web and Flutter payment architecture works, identify gaps, and propose the safest target architecture.

I specifically suspect that:

1. Country → payment-method assignment is not fully synchronized with the Vendor portal.
2. Vendors may not be able to configure their own payment methods correctly.
3. Some payment methods should be controlled at platform level.
4. Some payment methods should be available only in specific countries.
5. Checkout should consider BOTH marketplace country and the customer-selected transaction currency.
6. There appears to be an existing Vendor option allowing Admin/Platform to receive payment on the Vendor's behalf, but I do not know whether the complete backend accounting/settlement/payout flow is still wired correctly.

Audit all of this before changing behavior.

==================================================
1. CORE PAYMENT MODEL I WANT EVALUATED
==================================================

The desired high-level model is:

COUNTRY
→ determines which payment methods are legally/commercially available in that country

VENDOR
→ may enable/configure only payment methods that are available for the Vendor's country and permitted for Vendor configuration

CURRENCY
→ further filters methods at checkout according to currencies actually supported by each provider/method

CHECKOUT
→ displays only methods that satisfy the applicable country + currency + provider/configuration rules

COLLECTION MODEL
→ determines whether funds are collected directly by the Vendor or by AgendaAlly/platform on behalf of the Vendor

SETTLEMENT
→ if AgendaAlly collects Vendor funds, the resulting Vendor balance/liability must be accounted for correctly

PAYOUT
→ Vendor can request payout through the existing supported payout architecture, subject to permissions/status/business rules

This is the TARGET CONCEPT to compare against the existing implementation.

Do not assume the current code already implements it.

==================================================
2. IMPORTANT COUNTRY MODEL
==================================================

Payment availability should be country-aware.

Conceptually:

Country
  ↓
Allowed payment methods
  ↓
Vendor configuration
  ↓
Currency compatibility
  ↓
Checkout

For example, if a provider is assigned to Cameroon, Cameroon Vendors may be eligible to configure/use it according to provider rules.

If a provider is NOT available for Cameroon, a Cameroon Vendor should not be able to enable it merely because the provider exists globally.

Similarly, when AgendaAlly eventually operates in:

- United States
- Canada
- European countries
- United Kingdom
- other markets

those countries may have a different permitted provider set.

Audit whether the existing Country ↔ Payment Method relationship actually exists and where/how it is enforced.

==================================================
3. COUNTRY IS NOT THE SAME AS CURRENCY
==================================================

Do not treat country and currency as interchangeable.

A Vendor/business has an operating country.

A Customer/storefront may have a selected/display/checkout currency.

A payment provider may support:

- specific countries;
- specific currencies;
- both;
- or additional provider-specific restrictions.

The audit must determine what AgendaAlly currently stores for each of these concepts.

Identify whether currency is currently:

- display-only;
- conversion-related;
- order currency;
- payment currency;
- provider settlement currency;
- or some combination.

Do not infer behavior from UI labels alone.

Trace it through persisted data and payment requests.

==================================================
4. GLOBAL / PLATFORM PAYMENT METHODS
==================================================

Some methods may reasonably operate as platform-level collection channels.

Examples to investigate include providers such as:

- Stripe
- PayPal

and any equivalent global provider already present in the source.

The intended concept is that when a Customer checks out using a currency supported by such a platform-level provider—for example:

- USD
- CAD
- EUR
- GBP

and the provider is legitimately available for the applicable market/currency, payment may be collected by AgendaAlly/Admin.

The Vendor's share would then become an amount owed to the Vendor through the platform accounting/settlement/payout model.

DO NOT implement this merely from this description.

Audit whether the current architecture already supports this safely.
