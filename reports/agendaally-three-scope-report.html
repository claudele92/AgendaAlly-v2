5. Vendor-owned Product Shop Pickup

  • Reused the existing Product fulfillment choices: Delivery, Shop Pickup and Collection Point remain distinct. Product orders continue through native Cart/POS order paths and Shop-level order splitting. No Service booking, Specialist calendar, Driver or new branch model was introduced.
  • Scheduled policy is attached to an existing native Product ShopLocation (type1). Service locations (type2) and Collection Points are excluded. Some native location rows describe geographic/currency scope but lack a postal address: scheduled policy requires the location’s address, or the Shop’s public postal address only when there is one Product location. A single Shop address is not copied across multiple branches. Legacy ready-based pickup without a Product location remains valid without a fabricated branch/date.
  • The additive migration 2026_10_05_010000_add_native_product_pickup_scheduling.php adds branch-scoped shop_pickup_policies and nullable orders.pickup JSON. No orders are recreated/backfilled and no fulfillment flag is enabled automatically. An absent policy means As Soon As Ready. The owned development migration manifest/guard was updated for this addition.
  • Vendor My Shop shows pickup configuration only when Shop Pickup is enabled. It supports branch choice, ASAP or Scheduled, weekly enabled days with opening/closing times, explicit IANA timezone, preparation minutes, bounded window duration, same-day toggle/cutoff and blackout dates. Save/reload/reset use the native authenticated API. Capacity is clearly unlimited.
  • Pickup hours are separate from Shop business hours; there is no permanent inheritance or copy convenience action in this batch. One opening/closing interval per day is supported; overnight/split-shift schedules are not supported. Allowed windows are 30,60,90,120,180,240 minutes. The offered date horizon is 30 days.
  • ASAP means no reserved window or fabricated ready timestamp. Scheduled mode requires an explicit Vendor-selected location timezone because the existing Shop has no authoritative timezone field. Timestamps are stored as UTC ISO values, with local window labels and display in that IANA timezone; browser/server default timezone is not silently used.
  • Server availability filters closed weekdays, blackouts, preparation lead time, same-day disablement/cutoff, past/out-of-horizon dates and windows that do not fit pickup hours. Arbitrary Customer timestamps are not accepted as availability.
  • Public API: GET /api/v1/rest/shops/{shop}/pickup-availability with optional shop_location_id and date. It returns eligible Product locations, public location metadata and calculated windows, not private weekly/blackout rules.
  • Private API: GET/PUT/DELETE /api/v1/dashboard/shops/{shop}/pickup-policies/{location}. Existing shop_settings.view/manage grants are used; ownership remains unconditional through the native permission helper, intentionally supported Superadmin access remains, and view-only Staff cannot write. Foreign policies/branches and ungranted Staff are rejected server-side.
  • CartOrderService and POSOrderService derive/revalidate each Shop’s selected window inside the native order flow; policy/order checks lock the Product location inside a transaction. Blackout/disabled pickup/forged/stale windows are rejected before persistence. All-digital Shop groups bypass physical pickup calendar validation, preserving the native digital path.
  • orders.pickup stores timing mode, Shop and Product-location IDs, authoritative address/alias, timezone and nullable UTC window start/end. The whole multi-Shop selection map is stripped before persistence. No formatted display string is authoritative.
  • Customer checkout keeps per-Shop selections, shows branch/ASAP or date/server windows, clears stale/invalid selections and removes pickup state when switching to Delivery/Point. Legacy ASAP with no location has a local readiness marker which is not sent as order metadata. Backend validation remains the final authority.
  • Customer order cards/details and native Vendor order details display Shop Pickup plus local scheduled window or As Soon As Ready. Delivery-only details are not used for Pickup. The existing email order-summary template now uses pickup address/timing labels and avoids an epoch/fake date for ASAP; printable invoice templates/engine and notification delivery infrastructure were not changed.
  • Shop Pickup sets delivery_fee=0 and clears stale delivery address/address_id, location, tariff, Driver and Collection Point fields. It does not introduce a pickup fee or change Product price, taxes, commission, payment collection or FX. Delivery and Point bypass pickup policy rules.
  • Mixed-Vendor carts retain the native per-Shop order split and independent selections/policies; one Vendor’s schedule is not applied to all Shops. Existing common fulfillment eligibility still governs the cart; independently mixing different fulfillment types within one checkout was not redesigned.
  • The existing native ready Product-order status is reused; no new global Ready/Collected state machine or Driver assignment/dispatch operation was implemented. A dedicated future Ready-for-Pickup notification/collection handoff would need separate approval.

6. Capacity and other deliberate limits

Capacity remains unlimited. There was no appropriate Product pickup capacity/reservation mechanism to reuse safely, and Service/Specialist capacity was not repurposed. This avoids unsafe count-then-insert pseudo-capacity.

Concrete future proposal: add a per-location/UTC-window capacity row with a unique location/start/end key; atomically lock that row in the native order transaction, enforce a configured nullable limit, and reserve/release occupancy for the explicitly defined active/nonterminal Product order states. Revalidate policy and keep Customer retries idempotent. Prove simultaneous last-place requests, cancellation/release and multi-Shop rollback under the production database engine before enabling finite limits. This proposal is documentation only; no task/phase was started.

Other limits: scheduled pickup needs usable native Product-location postal metadata; one daily interval only; no overnight/split shifts; no physical media cleanup engine; no live cloud/provider calls. Browser acceptance gaps below remain open.
