  • Global deliveryman role and unrelated/other-shop invitations no longer make a driver assignable to the current Vendor.
  • Shop-owned assignment validates the exact order/shop, DELIVERY eligibility, global active driver account and authoritative active shop relationship before writing the existing assignment field.
  • Driver product-order reads, status/current changes and review target lookup cannot act on another assignee or an ineligible shop relationship. The ungrouped current-order OR was corrected and the target is authorized before updates.
  • Unassigned product-order listing/detail access and self-claim are closed without an explicit dispatch authorization contract.
  • Vehicle-setting access establishes the persisted owner before accepting a payload; replacing user_id cannot take over another driver's setting. Vendor deletion of a shared global setting is blocked.
  • Vendor driver status changes affect the shop relationship, not global account activation. Generic Vendor driver identity/credential/role editing and direct creation are contained.
  • Generic customer/staff profile projections no longer expose another shop's driver vehicle setting or other-shop invitations. Legitimate customer/staff identity rows remain available.
  • Forged location-event order IDs are filtered before dispatch; the queued listener captures the actor and rechecks assignment and active membership before broadcasting.

3. Existing invitations

Existing invitations were sufficient to represent the shop/user/driver relationship and acceptance. Only unambiguous accepted driver invitations are reused. No new identity, membership table, inferred membership or marketplace/demo driver record was created.

4. Additive migration/model field

One boolean, invitations.driver_active, defaulting to true, was necessary to suspend one shop relationship without changing users.active. Its model cast was added. Global inactivity still excludes a driver regardless of the default. The migration was tested up/down on isolated SQLite, then only that named migration was applied to the guard-proven owned development database. No historical migrations or seeders were run.

5. Exact authoritative membership rule

A driver is operationally eligible for a shop only when all of these hold:

  1. The native user has the global deliveryman role.
  2. The native global account is active.
  3. Exactly one invitation row exists for that exact shop/user pair.
  4. That row's role is deliveryman, status is Invitation::ACCEPTED, and driver_active is true.

Multiple exact-pair rows, including conflicting non-driver roles, are not chosen by row order. Driver authorization fails closed pending explicit reconciliation. Historical order assignment is not membership evidence.

6. Multi-shop behavior

Each exact shop/user relationship is independent. A legitimate accepted active relationship at Shop B remains eligible when Shop A suspends its relationship. No exclusivity assumption or global role replacement was added.

7. Global versus shop status

users.active remains global. Vendor driver suspension toggles only the accepted local invitation's driver_active. Pending or ambiguous driver relationships cannot use the legacy global toggle. The original non-driver Staff status behavior remains intact.

8. Vendor assignment authorization

The existing Seller path passes its actual current shop to the service. The order must belong to it, be a DELIVERY order, and the selected driver must satisfy the full membership rule. Forged driver/order/shop values do not widen the scope. Valid assignments still persist in orders.deliveryman_id.

9. Staff permission behavior

Existing shop authorization is retained: assignment uses orders.manage; driver/settings reads use staff.view; setting writes use orders.delivery_settings; membership status management uses staff.invite. No nonexistent orders.update permission or broader grant was introduced. Owner and permitted Staff paths are verified; missing permissions deny the operation.

10. Admin behavior

The separate authorized Admin assignment path retains its native global active-driver behavior without the Seller shop argument. Admin identity/global account controls remain separate. Admin assignment does not fabricate a shop membership: Driver product operations still require the explicit eligible relationship.

11. Unassigned orders and platform dispatch

No explicit product dispatch-pool authorization contract was established from the source. A global deliveryman role or the IN_HOUSE enum alone is not proof of authority. Product unassigned listing/detail/self-claim therefore fail closed. Eligible exact-assignee access is preserved for both native Seller and IN_HOUSE order types; no order was converted to IN_HOUSE. Separate Admin operations are retained.

12. Settings ownership

Reads/writes are scoped through the persisted setting's actual user and current shop authority. A submitted replacement user_id is rejected. Native validated vehicle, online and location fields remain supported. A Vendor cannot globally delete a shared setting; local suspension is the containment mechanism.

13. Unsafe provisioning

The native Vendor Add/direct Driver account path is unavailable and its server operation is blocked, including supplied passwords or verification values. Generic Vendor driver account editing is read-only/blocked. The shared service rejects a Driver creation request without a password rather than generating the predictable fallback. No new onboarding or token system was implemented.

14. Assignment payload

The existing modal now submits positive numeric deliveryman_id, not deliveryman. Existing selection is initialized only from server-returned eligible options; an ineligible prior driver is left unselected. Native success close/refetch behavior remains. The native type-2 Seller DELIVERY card is now reachable without relaxing the existing Ready/delivery-only Change condition.

16. Unresolved security areas

  • The separate Parcel/courier subsystem has no established Vendor-shop membership mapping. Its broader authorization questions were not redesigned or declared secured by this product-order work.
  • Wider Driver financial/customer projections, mobile APIs and a complete Driver DTO review remain deferred. This task is not a full application security certification.
  • Ambiguous invitation histories require explicit reconciliation.
  • Platform dispatch needs an explicit business/authorization contract before a product pool can be restored.
  • Native invitation deletion followed by a new accepted invitation can establish a fresh default-active relationship. Suspension is not an irreversible ban/tombstone policy.
  • Secure invitation/contact verification, promotion/onboarding and existing-account credential remediation remain later work; non-driver provisioning was not rewritten.

17. Active-assignment/offboarding ambiguity

Suspension removes active Driver product-order authority for that shop but preserves assignment IDs, order/history/current flags and Vendor/Admin visibility. There is no automatic reassignment, cancellation, order-state rewrite or financial cleanup. Handling an in-progress delivery when membership is suspended, restored or reinvited requires a later approved policy. Native self-history/report aggregates were not rewritten.
