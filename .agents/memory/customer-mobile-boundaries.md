name: Customer Mobile approval boundaries
description: Preserve the existing Flutter product; authentication repairs do not authorize financial or provider work.
---

Customer Mobile modernization must preserve the existing Flutter architecture, not rebuild or regenerate it. Completing an authentication/session campaign does not authorize booking, checkout, refund, policy, provider activation, backend or Web/Admin changes.

**Why:** The owner explicitly bounded Customer Mobile work and requires delivery of evidence followed by owner review before further implementation.

**How to apply:** Follow the current authorization for each campaign. Do not turn a passing auth check into permission to start financial work, activate providers, publish, or change the frozen Web assessment.

The owner treats Android as the first native qualification target. Android P0-02 closure requires actual Android persistence/erasure and lifecycle evidence; it does not qualify iOS Keychain behavior or authorize functional Phase 2 automatically.

**Why:** The owner explicitly requires Android-first and cross-platform/iOS qualification to be reported separately, followed by a stop for review even if Android passes.

**How to apply:** Keep platform-specific closure/counts separate and retain iOS native qualification as unexecuted unless separately authorized. Source configuration and Linux fixtures cannot close native storage.
