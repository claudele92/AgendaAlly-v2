name: SMTP approval boundaries
description: Owner-imposed limits on SMTP credentials, testing and other delivery paths.
---

The owner selected the normal Admin preview on port 3003 as the controlled MVP
integration-test environment. Do not create another isolated Admin preview or
another environment solely for SMTP testing. Use its existing encrypted Zoho
provider without retrieving, copying, replacing, exposing or logging the SMTP
credential. Allow only explicit Admin Test Email initially; general email remains
log-only/disabled, with verification, reset, booking and worker/scheduler mail
suppressed until individually approved. Keep payment providers, payouts/refunds,
SMS, push and other external integrations disabled/log-only. Preserve the normal
demo, protected baseline and SMTP encryption, password-free responses, verified
TLS and sanitized errors.

**Why:** The owner rejected another isolated preview after a preview mismatch and
explicitly chose the already configured normal Admin for controlled MVP testing.

**How to apply:** Keep the exception confined to the approved normal preview and
explicit Admin action, never general email or production/published runtimes.
Reuse existing verification rather than repeating broad acceptance campaigns.
After enabling the control, stop: the owner performs the first test from the
dashboard. Do not send an email or start another phase automatically.

The owner confirmed real mailbox receipt from the normal Admin flow and
required subsequent email-presentation investigation/correction to use source
inspection and local rendering without another SMTP connection.

**Why:** Delivery acceptance does not authorize additional sends, and correcting
recipient-visible assets must not weaken or expand the scoped transport.

**How to apply:** Build local Blade/MIME proof with send/postSend forbidden;
distinguish local presentation verification from corrected Gmail receipt.
Obtain explicit owner approval before any further real email.

A separately approved agent-controlled SMTP test permits only its specified
attempt using the provider in the approved runtime. Do not retrieve, replace, copy, expose
or log its stored SMTP password. Keep all other email paths suppressed and turn
the isolated permission off after the attempt. Never automatically retry a failed
or ambiguous result. Server acceptance alone is not final delivery confirmation;
the owner must confirm receipt.

**Why:** The owner explicitly bounded real-delivery approval to one Admin test,
required permission removal afterward, and distinguished SMTP acceptance from
actual mailbox receipt.

**How to apply:** Check saved-provider readiness and runtime provenance before
enabling anything. Never transfer the credential or create a replacement to
overcome a mismatch. Record only safe transport evidence. Earlier agent-send
approval does not override the later instruction that the owner sends first.

Safe SMTP diagnostics must preserve bounded stage events and numeric status
categories, not just generic debug activity levels. Never retain raw SMTP
dialogue, AUTH material or message bodies.

**Why:** Redacting all transport text to activity levels preserved secrecy but
left a completed owner attempt without an attributable SMTP failure stage or
server status. Activity patterns can support an inference, not a recovered
server rejection code or a frozen configuration snapshot.

**How to apply:** During read-only diagnosis, separate retained facts from
inferences and current settings. Do not retry or change configuration to fill
evidence gaps. Obtain approval before future diagnostic instrumentation or
another connection; correlate future safe events to one attempt.

The owner confirmed the corrected normal Admin Test Email logo,
Instagram/Facebook/LinkedIn icons and footer worked in Gmail, in addition to
SMTP transport and actual mailbox delivery. Treat that presentation baseline
as accepted; do not request another generic diagnostic send to re-prove it.
Verification/reset/selected-worker journeys still need their own acceptance.

**Why:** The owner explicitly confirmed the corrected recipient presentation
on 2026-10-05; local-only proof is no longer the limit for that Admin baseline.

**How to apply:** Reuse the accepted Admin receipt without generalizing it to
other email kinds. Any further connection, send, outbox deployment or
purpose-scoped delivery activation requires explicit approval; do not propose
a replacement isolated Admin solely to avoid the chosen normal environment.

Account-email certification requires its own controlled recipient/account authority;
never infer the recipient from the SMTP sender or use the owner's real Admin account.
An accepted generic Admin receipt does not close account or selected-worker gates.
Use the existing 20-gate rubric: C1/O4 start at 0.5 each and the baseline is 16/20.
Migration, code and local rendering are not certification evidence for full gate points.
The native account protocol is six-digit code entry, not an invented action-link flow.

**Why:** The owner approved a bounded C1/O4 campaign on 2026-10-05, prohibited another
generic SMTP test, and required at most one verification/reset journey only after
local checks and every recipient, isolation and account-safety condition passed.

**How to apply:** Complete authorized local work, then stop before real transport
when a recipient or safe account is missing. Report implementation and live
acceptance separately. Do not create action links or award points to bypass a gap.

Mailbox ownership is not permission to reuse an existing AgendaAlly account.
For new-disposable-only approval, any existing account association must stop
the attempt before modification, regardless of Customer/Admin/Vendor/Specialist
or other role.

**Why:** The owner expressly required a new disposable Customer only, with an
all-account collision check first and no modification if the email is already used.

**How to apply:** Check the owned native source read-only without role or
verified-status exclusions, and check related contact associations. Keep the
one-verification/one-reset cap and do not repeat the accepted Admin SMTP test.

The owner confirmed the selected verification email's actual Gmail receipt,
presentation, logo, social icons, content and layout on 2026-10-05.
Do not resend verification to re-prove this accepted mail baseline.

**Why:** The owner explicitly accepted those elements and prohibited a resend.

**How to apply:** Reuse that receipt/presentation acceptance, but check the
approved account's persisted verification status and runtime independently
before the reset stage. Mailbox receipt or a reported UI completion must not

Prepare the actual recipient's verification screen before a one-send-only
acceptance attempt; an agent-only browser session is not a recipient handoff.
Do not ask the recipient to restart signup to reach code entry after sending.

**Why:** Ordinary signup renews the current challenge even while SMTP is
suppressed. Later signup requests can leave new unsent messages and invalidate
the one authorized email's code; the short code lifetime also makes a delayed
chat handoff unreliable. The recipient-confirmed fresh-screen handoff later
completed verification with a matching native response and persisted state;
keep using that coordinated approach rather than an agent-only browser handoff.

**How to apply:** Coordinate the original code-entry session before issuance,
preserve that session, and separate receipt confirmation from persisted
verification. Diagnose expired/superseded challenges read-only; do not renew,
resend, force verification or clean pending records without applicable authority.

Additional queued reset requests do not inherit a one-email permission. An
explicit owner decision to keep the latest authorizes only cancellation of the
specified older unsent delivery/job and one processing attempt for the existing
current challenge, with the owner's normal code-entry screen ready. It does not
authorize a new request, Verification resend, unrelated mail or uncertain retry.

**Why:** The owner explicitly revised the scope after two unsent reset requests
were recorded, while preserving the one-real-email limit and receipt stop.

**How to apply:** Preserve the honest request history and frozen evidence,
prove older supersession/current binding before cancellation, preserve the
latest challenge, remove exact-record permission immediately after processing,
then stop for Gmail confirmation before normal UI completion.
